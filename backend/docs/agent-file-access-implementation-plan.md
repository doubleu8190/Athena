# Agent 文件访问改造方案

状态：待实施，尚未修改功能代码。审批、执行环境和工具限制见 [功能设计](agent-file-access-design.md)。

## 1. 改造范围

统一入口先判断权限和审批，再按部署配置选择 NativeExecutor 或 DockerExecutor。本地文件工具直接调用共用模块，Docker 固定入口调用同一模块；只有本地 shell 需要额外子进程。选中 Docker 后所有工具均进入沙箱，不自动降级。本次不建设新的审批系统或任务系统。

| 位置 | 修改内容 |
| --- | --- |
| application/tools/service.py、query_service.py | 集中判断路径范围、是否审批及执行方式，查询与执行采用同一规则 |
| application/orchestration/worker_tools.py、worker_workflow.py | 目录外文件审批、shell 默认审批；恢复原批准参数，结果读取也经过统一入口 |
| application/orchestration/root_workflow.py、plan_materialization.py | 记录目录版本和本次执行环境，模型不能自行填写 |
| infrastructure/tools/native.py | 显式本地执行实现，移除“Docker 失败后自动本地执行”的语义 |
| configuration/settings.py、backend/.env.example | 将 sandbox_enabled 默认值和示例改为 false，sandbox_required 保持 false；保留用户显式配置 |
| infrastructure/integrations/sandbox/docker_runner.py | 固定程序、默认和单次批准挂载、输出上限、容器停止与恢复 |
| bootstrap/postgres.py、app.py | 组装设置服务和所选执行器，按需初始化 Docker，不影响未启用沙箱的启动 |
| 前端 Settings、Tools、Approvals | 简化状态，保留原审批设置，展示目录外实际授权范围和运行环境 |

新增目录设置 ORM/repository/controller、共用文件操作模块和 Docker 工具入口、镜像。复用现有分层与执行账本；read_worker_result 本地模式使用受控结果读取，Docker 模式由后端按当前任务 result_ref 提供有限数据给容器，不暴露宿主机存储路径。它也必须经过统一审批判断，关闭或未配置目录时不能绕过审批。

## 2. 设置与状态

新增单行 agent_file_access_settings 表，字段为 id=1、enabled、root_path、root_device、root_inode、revision、updated_at。enabled 表示是否开启目录内免审，不是工具总开关。默认 false、revision=0；首次插入不覆盖旧值。数据库为唯一目录设置来源，不修改用户 .env。

保留 GET /api/settings，新增 GET、PUT /api/settings/file-access：
~~~json
{"enabled": true, "root_path": "/Users/me/agent-workspace", "expected_revision": 6}
~~~

响应除保存字段外只返回：

- directory：status、reason。
- sandbox：status、reason，status 区分 disabled、ready、unavailable；disabled 表示使用本地模式。
- shell_enabled：沿用原工具开关。

不再返回多组 availability/available 布尔值。目录未配置或免审关闭时，工具保持可用，只是全部审批。沙箱方式继续由 SANDBOX_ENABLED / SANDBOX_REQUIRED 决定，两者均默认 false，未显式配置就使用本地；显式选中 Docker 后故障不降级，旧任务也不能静默更换环境。

保存接口检查身份及来源，即使关闭登录也防止跨站修改。取得单一执行锁后核对 expected_revision，非空目录才验证路径、设备和 inode；修改目录或免审开关时递增版本。省略 root_path 保留旧值，null 允许清空，清空后不管 enabled 值如何都全部审批。关闭免审不要求旧目录仍存在。版本冲突或目录忙返回 409，非法路径返回 422，身份或来源错误返回 401/403，数据库不可用返回 503。失败保留旧设置及前端草稿，不自动覆盖。

## 3. 审批与单次授权

复用 require_approval，不增加审批策略枚举或固定开关错误码。先检查工具启用状态和任务白名单，再按下面的顺序决定是否审批：

- 免审关闭、目录未配置或不可用：所有 Agent 工具都需审批，优先于工具自身的 require_approval。
- 免审有效：基础文件工具访问目录外必须审批；目录内按工具设置执行，默认免审。
- 其他操作按工具设置执行，shell 默认 true；用户主动提高审批要求仍生效。风险等级不使基础文件工具隐式必审。

没有有效默认目录时，文件工具必须提供绝对路径，不使用服务 cwd。shell 必须明确工作目录：本地使用宿主机绝对目录，Docker 可使用获准的目录映射，或镜像内不连接宿主机的固定临时目录 /tmp。参数不足先补全，不因缺少默认目录禁用工具。相对文件路径仅在存在有效配置目录时解析，与免审开关是否开启无关。

需要审批时展示实际目标、读写类型和有效访问范围，批准只对应本次调用。对 Docker 写入，页面同时显示原子替换所需的父目录访问范围，未获批准就不挂载、不执行。

Docker shell 的 additional_paths 示例：
~~~json
{"command":"head /approved/input","additional_paths":[{"name":"input","path":"/data/input.csv","access":"read"}]}
~~~
每项固定为 name、path、access：path 是宿主机绝对路径，access 为 read 或 write（读写），源必须存在；新建文件申请父目录。name 唯一、只含字母数字和下划线、不以数字开头、最多 32 字符，映射到 /approved/<name>，不能传任意容器挂载位置。命令按固定路径编写，审批同时展示两侧路径和权限；后端不修改已批准命令。未配置默认目录时，还需明确 cwd，可选已批准的目录映射或不连接宿主机的 /tmp。本地 shell 不接受非空 additional_paths，命令直接使用宿主机路径；工具说明标明当前环境。

沿用 Worker 暂停 → ApprovalRecord/Outbox → resume_worker。审批保存原始目标、已检查的实际路径、访问类型、有效挂载范围、参数、目录 revision、执行环境、Docker 镜像 digest（如有）和 operation_key，整体计算 args_hash，复用现有审批 JSON 字段。

执行前重新检查路径及父目录信息、任务身份、租约和数据库中的批准记录。目标或授权范围发生变化则本次批准失效；不接受模型自报 approved。审批前不读取目录外正文。操作系统权限、自保位置、特殊文件及不支持的路径仍可使已批准请求失败。

本地 shell 的批准只授权整条命令，不逐项审批脚本内部读写。用户若主动关闭 shell 审批，会放宽这一默认保护；不能据此宣称本地 shell 仍具有目录隔离。

## 4. 执行与路径处理

~~~text
检查工具、enabled、allowed_tools、参数和实际路径范围
→ 核对目录版本和执行环境，必要时审批
→ 取得统一执行锁，复查环境和批准范围
→ 用短事务 claim 执行账本，不长期持有 run/task 行锁
→ 本地调用共用模块，或启动 shell / Docker 运行器
→ 等模块实际返回或确认运行器停止，保存结果，释放锁
~~~

Domain 使用 dataclass，Application 用明确模型检查参数和审批数据；目录版本、镜像和挂载计划由后端填写。相对路径以默认目录为起点，绝对路径允许申请目录外访问；拒绝 ..、NUL、URI 等输入，禁止未检查的变量或通配符展开。

共用文件操作模块逐段检查实际目标，禁止跟随符号链接，拒绝当前目标为多硬链接、FIFO、设备或 socket。列表不跟随链接，不检查无关子树。用目录句柄、O_NOFOLLOW、fstat 等接口防止检查后替换路径；无法可靠检查的挂载边界直接报错。本地直接调用该模块，容器通过固定入口调用，不为本地普通读写增加子进程、JSON 通信或 PID 登记。

Docker 有有效配置目录时挂到 /workspace；基础文件工具的目录外目标映射到 /approved/target，shell 额外目标按上面的命名规则映射。读目标只读，写入父目录只有审批明确获准后才读写挂载，调用结束即移除。未配置目录时不增加默认宿主机挂载。挂载不递归引入其他挂载点，源不存在时报错；Docker 无法对应后端路径时返回部署配置错误，不用宿主机代执行。

**大目录方案建议，待确认：** 普通文件工具不全树扫描；Docker shell 增加可选 workspace_path，只挂载本次所需的宿主机子目录到 /workspace，cwd 相对此挂载解析，默认 "."。workspace_path 未传时沿用有效配置目录，没有配置目录则必须明确本次工作目录。它属于审批范围，改变后重新审批；仅改变 cwd 不声称缩小了挂载。

建议去掉固定 10,000 项的 shell 拒绝门槛，硬链接和挂载检查改为流式扫描，只保留可配置时限。超过检查预算返回 scope_check_incomplete，不启动命令、不跳过检查；提示使用更小的 workspace_path，或由用户调整预算后重新调用。不引入全树缓存和监听器，不自动排除 node_modules 等依赖目录；普通文件工具不受该次扫描失败影响。此项只记录建议，尚未作为已确认接口。

文件操作遵守功能设计的分页、大小和原子写入要求：比较 expected_sha256，再写同目录临时文件并 flush/fsync；create 不能覆盖已有目标，replace 原子替换。两种环境用同一逻辑。Docker 下全部读写在容器完成，不由后端偷偷写回。保留 ToolExecutionResult，output 为 JSON，error 为约定错误码。

## 5. 单一执行锁与异常恢复

第一版使用一把系统级跨进程执行锁，所有 Agent 工具和目录设置变更串行处理，包括单次访问目录外文件。省去配置锁、目录读写锁和目标文件锁三套协调，不承诺同一实例内文件工具并行。审批等待和模型调用不持锁，数据库行锁只用于短事务。

运行前再次核对任务的目录 revision 和执行环境，计划修订、重试和恢复保留原值；改变目录或本地/Docker 模式后，旧任务返回配置已变化，不补写新版本。模型不能自行设置后端专用执行字段。

本地文件工具不启动独立运行器：使用现有执行账本记录结果，取消后等待正在进行的实际读写结束再释放锁；后端进程退出后不会遗留独立文件工具进程。只读失败正常报错，写入结果无法确认则 outcome_unknown，不自动重写。不为这些调用登记 PID 或增加运行器握手。

Docker 和本地 shell 的恢复流程如下，不因 outcome_unknown 永久占住目录：
1. 对已过期租约的执行记录检查运行器。Docker 用 operation_key 派生的容器名和标签；本地用主机标识、进程组和启动时间核对身份，避免误杀复用 PID。
2. 尝试停止本系统的运行器，并在有限时间内检查结果，建议每次最多等待 5 秒。由启动、下一次工具请求或用户“重新检查”触发，不另建后台轮询任务；重复检查和停止应安全，不影响仍有有效租约的其他 Worker。
3. **确认停止**：有已保存结果就沿用；否则终结原记录，只读操作记为失败，写入或 shell 记为失败且 error=outcome_unknown。释放锁，允许新操作；原调用不自动重跑，也不复用一次审批再执行。
4. **无法确认停止**：保留未终结记录，只暂停工具执行和切换工作目录/环境。Settings 仍可查看具体运行标识、原因及处理提示，并提供“重新检查”操作。
5. 管理员停止对应容器或进程后，再次检查即可解除暂停；不提供直接清除记录、跳过停止检查的按钮。

复用执行账本，runtime_json 只保存需要管理的 Docker 或本地 shell 运行标识，不用于普通本地文件调用，不新增恢复表或状态机。本地 shell 启动包装程序可先等待父进程保存运行标识，再接收实际命令；不把这套握手扩展到基础文件工具。启动、下一次工具执行及重新检查共用同一恢复函数，恢复结果和晚到结果以短事务确保原结果只保存一次。

本地任意 shell 若主动脱离登记的进程组，无法保证自动清理完整进程树；需报告并由管理员处理。严格的子进程隔离和终止保证只适用于 Docker，不能把本地进程组当作沙箱。

## 6. 资源与部署

shell 和 Docker 沿用现有 60 秒执行超时、1,000,000 字节输出上限；Docker 默认 1 CPU、512 MiB、128 PID，临时目录建议限 64 MiB。基础工具仍有 1 MiB 文件、200 行/64 KiB 读取和分页上限。原生文件调用的等待超时不能视为系统 I/O 已停止，必须等实际读写结束再释放锁，不能虚报强制终止。

本地不依赖 Docker，不承诺容器级 CPU、内存或进程限制。第一版不做工作目录总磁盘配额，尤其不能用临时目录限额代表 shell 的总写入上限；磁盘不足返回明确错误，可能已完成的 shell 修改不回滚。需要总容量硬限制时再增加文件系统配额方案。

本地直接使用服务账户可见路径；Docker 使用同一默认目录与本次批准的附加路径，确认 Docker 服务路径映射和容器 UID/GID 权限。Athena 容器化部署本身不自动开启工具沙箱。未启用沙箱时不初始化 Docker 连接；已启用但不可用时拒绝工具，禁止自动降级。

初始化默认设置、补齐工具定义并保留已有启用/审批偏好。将 Settings.sandbox_enabled 和环境示例默认改为 false，sandbox_required 保持 false，不覆盖用户 .env 的显式选择。新目录表和执行账本 runtime_json 提供建表/加列 SQL；create_all 只负责新表，不能代替已有表加列。只在 Docker 模式构建并检查工具镜像，本地只使用共用模块，无需镜像或固定程序进程。

## 7. 页面与验收

Settings 将 enabled 标注为“允许配置目录内免审批”，关闭或未配置时提示“所有操作需审批”，不显示为工具故障。审批页展示实际授权范围，以及 Docker 附加路径两侧的映射；Tools 沿用原设置，但注明全局免审关闭和目录外规则不能被覆盖。不原样把正文、写入参数或 shell 输出放到时间线，详情遵守会话权限。

GET /api/settings/file-access/execution 返回当前阻塞操作的编号、运行器标识、原因和处理提示；POST /api/settings/file-access/recheck 触发恢复检查并返回同样的状态。两者使用设置管理认证；重新检查不能接受任意 PID/容器名或直接清除记录，不增加重复的工具可用布尔值。旧任务或审批缺少新目录、环境及授权范围时，保留历史但不继续执行。纯模型回答和管理查询不受工具暂停影响。

| 验收场景 | 要求 |
| --- | --- |
| 无 Docker、本地模式 | 基础工具和 shell 可用，不尝试连接 Docker |
| 未设置环境变量、已有显式 Docker 配置 | 前者默认本地，后者保留 Docker 选择，不被升级覆盖 |
| 免审关闭、目录为空或无效 | 所有可调用工具都审批，包括 read_worker_result；不因免审关闭而禁用工具 |
| 未配置目录的相对路径和 shell 工作目录 | 提示补全绝对目标或明确 cwd，不采用后端代码目录 |
| 两种模式中的目录内/外读写 | 默认目录内免审，目录外先审批；拒绝或篡改批准不执行 |
| Docker 目录外读写 | 只使用本次批准的有效挂载范围，写父目录授权明确，执行后移除 |
| shell 命令及附加路径 | 容器路径按 name 固定生成；命令不自动改写，本地不接受非空 additional_paths |
| 普通文件工具的链接、目录和挂载检查 | 只检查当前目标，不扫描无关子树；大目录 shell 方案另待确认 |
| 本地文件工具实现 | 直接调用共用模块，不为每次读写启动或登记子进程 |
| Docker 中先写越界脚本再执行 | 未批准路径不可见，模块和子进程不能增加授权 |
| Docker 故障、修改执行模式 | 已选 Docker 不降级；旧批准不能转到本地执行 |
| Worker 崩溃或结果未知 | 确认运行器停止后可继续新任务，原操作不自动重跑 |
| 无法停止、人工处理后重新检查 | 只暂停相关执行，管理可用，核验后解除，无无条件解锁 |
| 并发任务、配置变更、写入冲突 | 串行执行，旧目录版本不误操作新目标，hash 冲突不覆盖 |
| 超时、输出、磁盘不足 | 限制可测，错误明确，不虚报未修改或具备磁盘配额 |

顺序：统一审批和可选运行器 → 设置与单次授权 → 文件工具及 Docker 挂载 → 单锁与恢复 → 页面与验收。两种模式分别测试；容器隔离必须使用真实 Docker，持久化恢复使用真实 PostgreSQL，补充前端类型/构建检查和真实模型场景，记录尚未验证的保证。
