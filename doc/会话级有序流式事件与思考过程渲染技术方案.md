# 会话级有序流式事件与思考过程渲染技术方案

## 1. 文档目的

本文设计 Athena 会话级事件推送协议，解决以下问题：

- 同一 `session_id` 内，Durable Event、Realtime Event、工具事件、思考事件和回答 Chunk 的顺序一致。
- 同一个回答流或思考流中的多个 Chunk 可以可靠组装、去重和恢复。
- SSE 断线重连后不会因为多个 Chunk 共用逻辑事件 ID 而丢失或重复内容。
- 前端可以分别渲染回答内容、思考摘要、工具调用和运行状态。

本文基于当前实现中的 [events.py](../athena/gateway/routes/events.py)、[agent_store.py](../athena/infrastructure/sqlite/agent_store.py)、[transport.py](../agent_runtime/transport.py)、[streaming.py](../agent_runtime/streaming.py) 和 [useSessionEventStream.ts](../frontend/src/hooks/useSessionEventStream.ts) 设计。

## 2. 设计边界

本文讨论的是同一会话内的有序性，不要求不同 Session 之间存在全局顺序。

“思考过程”指用户可见的执行阶段、工具调用、检索摘要和受控的思考摘要，不直接展示模型隐藏的原始 Chain-of-Thought。原始模型 Token 只在 Runtime 内部处理，并通过合并器转换为可展示事件。

## 3. 核心结论

事件需要同时拥有两种顺序信息，并通过 `stream_id` 完成内容归组：

```text
session_seq              会话级顺序和 SSE 恢复游标
stream_id + chunk_id     逻辑 Stream 归组和 Stream 内内容顺序
```

其中 SSE 的 `id` 必须使用 `session_seq`。不再设置独立的逻辑事件 ID，多个 Chunk 通过相同的 `stream_id` 归组。

示例：

```text
session_seq=101  stream_id=answer-1  chunk_id=1
session_seq=102  stream_id=null      chunk_id=null
session_seq=103  stream_id=answer-1  chunk_id=2
session_seq=104  stream_id=answer-1  chunk_id=3  complete=true
```

## 4. 当前实现的问题

### 4.1 Durable 和 Realtime 使用两条发送路径

当前 Durable Event 写入 SQLite 后广播，Realtime Event 直接进入内存队列。Realtime Event 的 `event_id` 为 `None`，不参与 SQLite 游标。

SSE 当前每轮先读取 SQLite，再读取 Realtime 队列。这会导致队列中的 Realtime Event 被后写入的 Durable Event 超越：

```text
Realtime R1 已进入队列
Realtime R2 已进入队列
SSE 发送 R1
Durable D 写入 SQLite
SSE 下一轮先发送 D
SSE 再发送 R2
```

实际顺序可能变成：

```text
R1 -> D -> R2
```

### 4.2 stream_id 不能作为 SSE 游标

`stream_id` 用于 Stream 归组，不表示事件在会话中的位置。如果多个 Chunk 使用相同的 SSE `id`，断线时浏览器只能上报共享的 ID，服务端无法判断客户端已经收到哪个 `chunk_id`。因此 `stream_id` 和 SSE 恢复游标必须分离。

### 4.3 当前 StreamCoalescer 没有形成端到端协议

当前 `StreamCoalescer` 已经维护版本和字节偏移，但主 Harness 仍直接发送原始 `message.delta`，而 `CommandConsumer` 又在 Graph 完成后额外发送一整段内容。这可能造成重复追加和临时渲染错误。

## 5. 目标事件模型

### 5.1 事件 Envelope

```json
{
  "schema_version": 2,
  "session_seq": 104,
  "event_type": "message.delta",
  "durability": "durable",
  "session_id": "session-1",
  "run_id": "run-1",
  "stream_id": "stream-answer-1",
  "stream_type": "answer",
  "chunk_id": 3,
  "is_complete": true,
  "producer_id": "runtime-main",
  "payload": {
    "delta": "最终一段内容",
    "start_offset": 20,
    "end_offset": 28
  },
  "occurred_at": "2026-08-31T10:00:00Z"
}
```

字段规则：

| 字段 | 规则 |
| --- | --- |
| `session_seq` | 同一 Session 内所有前端可见事件唯一递增 |
| `stream_id` | Stream 的逻辑归组 ID，回答流和思考流必须区分；同一 Stream 的 Chunk 共用 |
| `stream_type` | `answer`、`thinking`、`tool_output` 等 |
| `chunk_id` | 同一 `stream_id` 内从 1 开始严格递增 |
| `is_complete` | 只有最后一个 Chunk 可以为 `true` |
| `start_offset` | 可选，内容 UTF-8 字节起点 |
| `end_offset` | 可选，内容 UTF-8 字节终点 |

### 5.2 SSE 格式

```text
id: 104
event: message.delta
data: {"session_seq":104,"stream_id":"stream-answer-1",...}
```

浏览器的 `Last-Event-ID` 对应 `session_seq`，而不是 `stream_id`。

## 6. SessionEventBus

所有事件必须通过统一的会话级事件总线：

```text
Runtime / Tool / File Worker / Sub Agent
                    |
                    v
             SessionEventBus
                    |
          按 session_id 串行化
                    |
          分配 session_seq
                    |
          持久化并广播
```

每个 Session 使用一个逻辑串行处理器：

```text
session-A -> worker-A -> subscriber queues
session-B -> worker-B -> subscriber queues
```

事件发布流程：

1. 生产者向 `SessionEventBus.publish()` 提交事件。
2. 事件进入对应 Session 的内部队列。
3. Session Worker 取出事件并分配 `session_seq`。
4. 如果事件需要恢复，则写入 Event Store。
5. 对 Stream 事件分配或校验 `chunk_id`。
6. 持久化成功后投递所有订阅者队列。

当前 `RealtimeTransport` 的锁只保护订阅者集合，`queue.put()` 在锁外执行，因此不能单独承担会话级排序职责。

## 7. 持久化和广播一致性

推荐使用“持久化事件 + 订阅通知”的模型：

```text
分配 session_seq
    -> 写 agent_events
    -> 提交事务
    -> 投递 subscriber queue
```

事件写入和队列投递不是跨系统原子操作，因此必须允许以下恢复路径：

- 数据库已提交、队列投递失败：后续 SSE 重连通过 Event Store 重放。
- 数据库已提交、进程在广播前崩溃：重连通过 `Last-Event-ID` 恢复。
- 队列满：生产者等待背压，不丢弃 Durable Event。

如果需要精确恢复回答和思考摘要，合并后的 Chunk 也应持久化。原始 Token 不需要逐条持久化。

## 8. 数据库模型

可以在现有 `agent_events` 基础上扩展：

```sql
CREATE TABLE agent_events (
    session_id TEXT NOT NULL,
    session_seq INTEGER NOT NULL,
    run_id TEXT,
    stream_id TEXT,
    stream_type TEXT,
    chunk_id INTEGER,
    is_complete INTEGER NOT NULL DEFAULT 0,
    event_type TEXT NOT NULL,
    durability TEXT NOT NULL,
    producer_id TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    occurred_at TEXT NOT NULL,
    PRIMARY KEY (session_id, session_seq),
    UNIQUE (session_id, stream_id, chunk_id)
);
```

这里的 `session_seq` 是会话级事件游标。为了保持现有协议兼容，数据库中的旧 `event_id` 列可以暂时作为 `session_seq` 使用，但对外协议应统一使用 `session_seq`。

推荐使用以下命名，避免语义冲突：

```text
session_seq       会话级唯一游标
stream_id         Stream 的逻辑归组 ID
chunk_id          Stream 内 Chunk 序号
```

`stream_id` 同时承担逻辑归组和具体内容流标识，不再额外维护逻辑事件 ID。

## 9. Chunk 分配和幂等

`chunk_id` 必须由服务端生成或校验，不应完全依赖生产者本地计数器。

建议使用幂等键：

```text
idempotency_key = stream_id + ":" + chunk_id
```

重复发布时：

```text
已存在且内容一致 -> 返回已有事件
已存在但内容不同 -> 拒绝并记录协议错误
```

Stream 状态机：

```text
created -> streaming -> completed
                    \-> failed / cancelled
```

一旦出现 `is_complete=true`，服务端记录 `final_chunk_id`，后续更大的 Chunk 必须拒绝。

## 10. StreamCoalescer 设计

原始 LLM Token 通过合并器形成可展示 Chunk：

```text
LLM Token
   -> StreamCoalescer
   -> 50ms 或 512 bytes 触发刷新
   -> message.delta Chunk
   -> SessionEventBus
```

每次刷新生成：

```text
chunk_id = previous_chunk_id + 1
start_offset = previous_end_offset
end_offset = start_offset + utf8_bytes(delta)
```

最后一次刷新时设置：

```text
is_complete = true
```

空响应不需要发送空字符串 Chunk，可以直接发送 `message.completed` 并将 Stream 标记为完成。

当前 `StreamCoalescer` 中的 `_version` 可以转为 `chunk_id`，现有 `start_offset`、`end_offset` 可以继续用于内容连续性校验。

## 11. 事件类型设计

### 11.1 回答流

```text
message.started
message.delta
message.completed
```

`message.delta` 负责增量内容，`message.completed` 负责生命周期确认。

### 11.2 思考摘要流

```text
thinking.started
thinking.summary
thinking.completed
```

示例：

```json
{
  "event_type": "thinking.summary",
  "stream_id": "stream-thinking-1",
  "chunk_id": 2,
  "is_complete": false,
  "payload": {
    "content": "正在检查事件存储和 SSE 重连逻辑"
  }
}
```

思考摘要应该是应用生成的可控文本，不应直接暴露模型内部完整推理链。

### 11.3 工具和运行事件

```text
run.started
run.completed
run.failed
tool.started
tool.completed
retrieval.started
retrieval.completed
```

这些事件通常不需要 `chunk_id`，但必须拥有 `session_seq`，并参与会话级排序。

并行子 Agent 使用独立的 `run_id` 和 `stream_id`，通过 `parent_run_id` 关联父运行。

## 12. SSE 重放流程

SSE 端点不再采用“先查 SQLite、再读 Realtime 队列”的双路径，而是依赖统一事件总线。

连接流程：

1. 读取 `Last-Event-ID`，得到 `after_seq`。
2. 在 SessionEventBus 中注册订阅者。
3. 原子取得 `replay_watermark`。
4. 重放 `after_seq < session_seq <= replay_watermark` 的事件。
5. 消费 `session_seq > replay_watermark` 的实时事件。
6. 之后只消费统一队列。

伪代码：

```python
subscriber, watermark = await event_bus.open_subscription(
    session_id,
    after_seq=after_seq,
)

for event in await store.events_between(
    session_id,
    after=after_seq,
    upto=watermark,
):
    yield encode_sse(event)

async for event in subscriber:
    if event.session_seq > watermark:
        yield encode_sse(event)
```

重放和实时队列出现重复时，按会话级 `session_seq` 去重。

## 13. 前端渲染模型

前端应维护两级 Reducer：

```text
SessionReducer
  校验 session_seq，并维护会话游标

StreamReducer
  按 stream_id + chunk_id 组装具体内容
```

每个 Stream 的状态：

```ts
type StreamState = {
  streamId: string
  runId: string
  nextChunkId: number
  finalChunkId: number | null
  content: string
  status: "created" | "streaming" | "completed" | "failed"
  pending: Map<number, ApplicationEvent>
}
```

Chunk 处理规则：

```text
chunk_id < nextChunkId -> 丢弃，表示重复
chunk_id == nextChunkId -> 应用并继续消费 pending
chunk_id > nextChunkId -> 暂存，等待缺失 Chunk
is_complete == true -> 记录 final_chunk_id
```

事件投影：

```text
message.delta       -> assistant 消息
thinking.summary    -> 思考面板
tool.started        -> 创建工具卡片
tool.completed      -> 更新工具卡片
message.completed   -> 确认回答完成
run.completed       -> 结束运行状态
```

`message.completed` 不应再简单覆盖字符串，而应使用最终 `StreamSnapshot` 校验内容。

## 14. Snapshot 设计

每个 Stream 维护一个最新快照：

```json
{
  "stream_id": "stream-answer-1",
  "run_id": "run-1",
  "stream_type": "answer",
  "version": 3,
  "last_chunk_id": 8,
  "content": "完整回答内容",
  "status": "completed",
  "updated_at": "2026-08-31T10:00:00Z"
}
```

断线重连时可以采用：

```text
先重放事件 -> 检测 Chunk 缺口 -> 请求或接收 Snapshot -> 继续接收新 Chunk
```

思考面板也应有 Snapshot，否则思考 Realtime Event 丢失后无法恢复当前阶段。

## 15. 迁移步骤

### 阶段一：协议扩展

- 增加 `session_seq`、`stream_type`、`chunk_id`、`is_complete`。
- 保留旧字段一段时间，服务端同时输出兼容字段。
- 为 `(session_id, stream_id, chunk_id)` 增加唯一约束。

### 阶段二：统一发布入口

- 新增 `SessionEventBus`。
- 所有 Runtime、文件任务、审批、工具和子 Agent 事件统一进入总线。
- 禁止直接调用 `RealtimeTransport.publish()`。

### 阶段三：改造流式输出

- Harness 的原始 Token 不再直接作为客户端事件发送。
- 使用 `StreamCoalescer` 生成带 `chunk_id` 的合并 Chunk。
- 删除 `CommandConsumer` 在 Graph 完成后再次发送整段内容的逻辑。
- 最终只发送完成事件和 Snapshot。

### 阶段四：改造 SSE

- `Last-Event-ID` 改为会话级 `session_seq`。
- 使用 replay watermark 完成历史重放和实时队列切换。
- 统一处理重复事件和连接关闭。

### 阶段五：改造前端

- 将 [useSessionEventStream.ts](../frontend/src/hooks/useSessionEventStream.ts) 改为事件 Reducer。
- 增加回答流、思考流和工具活动状态。
- 增加 Chunk 缺口检测、重复丢弃和 Snapshot 恢复。

## 16. 测试方案

必须覆盖以下场景：

```text
Chunk 1 -> Durable Event -> Chunk 2
Chunk 1 -> Chunk 2 -> Durable Event
多个并发子 Agent 同一 Session
初始化重放期间产生新 Chunk
SSE 在任意 Chunk 后断线
重复 Chunk
跳号 Chunk
完成后继续发送 Chunk
队列满时的背压
Snapshot 恢复后继续接收 Chunk
```

核心断言：

```text
同一 Session：session_seq 严格递增
同一 Stream：chunk_id 严格递增
重复 Chunk：不会重复渲染
跳号 Chunk：不会直接破坏内容顺序
完成后：Stream 内容等于最终 Snapshot
重连后：事件不会丢失，允许幂等重放但不能产生重复内容
```

## 17. 最终方案

最终协议采用以下职责划分：

```text
session_seq              会话级事件顺序和 SSE 恢复
stream_id + chunk_id     Stream 逻辑归组和内容顺序
is_complete              最后 Chunk 标识
SessionEventBus          会话级串行化和广播
Event Store              事件恢复
StreamCoalescer          控制高频流量
StreamSnapshot           最终状态恢复
Frontend Reducer         顺序校验和 UI 投影
```

这样可以表达并恢复如下事件序列：

```text
回答 Chunk 1
  -> 工具开始
  -> 思考摘要
  -> 回答 Chunk 2
  -> 回答 Chunk 3（is_complete=true）
  -> message.completed
```

其中每个事件拥有唯一的会话级 `session_seq`，同一个回答或思考流则通过共享的 `stream_id` 和递增的 `chunk_id` 进行组装。
