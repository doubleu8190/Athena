# 登录自动续期设计

日期：2026-11-09

状态：产品规则已确认；本文接口、字段、迁移和实现细节为待整体确认的实施建议。本文不代表实施授权，也未经过独立代码审查。

## 1. 目标与已确认规则

让持续使用 Athena 的用户保持登录，同时让长期闲置的登录自然失效。

| 场景 | 规则 |
| --- | --- |
| 普通登录、注册后自动登录 | 闲置窗口为 7 天 |
| 勾选“记住我”登录 | 闲置窗口为 30 天 |
| 持续主动使用 | 自动向后延长有效期，不设累计登录时长上限 |
| 主动使用 | 用户主动操作触发请求，例如发送消息、打开会话、查看知识库、修改配置 |
| 非主动使用 | 后台轮询、自动重连、Agent 后台运行、页面仅保持打开，均不续期 |
| 触发方式 | 前端在主动操作时调用专用续期接口，正常情况下最多每 5 分钟一次 |
| 时间精度 | 有效期以最近成功续期为基准，接受与最后一次操作相差约 5 分钟；网络故障期间可能更久 |
| 临时失败 | 保留当前登录状态，下次主动操作重试，不将网络或服务故障当作退出 |
| 明确失效 | 会话过期或撤销时提示重新登录，保留页面未发送内容 |
| 多标签页 | 同一浏览器配置文件中共享同一认证 Cookie 的标签页共享续期、退出状态 |
| 多设备 | 不同浏览器或设备的独立登录会话分别计时，互不续期 |

续期不阻塞业务操作；业务请求独立执行正常认证。过期或撤销的会话不能通过续期恢复。

## 2. 已核对的当前实现

- `backend/src/app/auth/service.py`：普通会话固定 7 天，“记住我”固定 30 天。注册使用普通期限；`authenticate` 只读验证，不续期。
- `backend/src/domain/auth/model/entity.py`：`AuthSession` 保存 token 摘要、过期时间、撤销时间、创建时间，没有续期窗口字段。
- `backend/src/adapter/auth/model/auth.py`：`auth_sessions` 对应上述字段，token 摘要唯一。
- `backend/src/adapter/auth/repository/auth.py`：有效会话要求 `expires_at > now`、未撤销，且用户 active、未删除；登出撤销当前会话；修改密码保留当前会话并撤销其他会话。
- `backend/src/api/auth.py`：注册、登录设置 HttpOnly、SameSite=Lax Cookie，Max-Age 与初始会话期限一致；已有 Cookie 设置和清理函数；认证响应使用 `Cache-Control: no-store`。
- `backend/src/api/security.py`：从 Cookie 认证；写请求复用既有 Origin 校验。
- `backend/src/adapter/auth/repository/transaction_guard.py`：已有事务内身份复核采用先 users、后 auth_sessions 的锁顺序，取得锁后读取时间并判断有效性。
- 当前仓库未发现前端工程；本文前端部分是后续接入契约，不能将仅后端完成视为完整用户体验交付。

本设计保持现有服务端会话、Cookie 和分层结构，不引入 JWT、refresh token、Redis 或定时续期 Worker。

## 3. 续期接口建议

新增 `POST /api/v1/auth/renew`，无请求体，凭现有认证 Cookie 识别当前会话。客户端不能指定用户、会话 ID 或续期天数。

成功返回 HTTP 200：

```json
{"expires_at": "2026-11-16T08:00:00Z"}
```

同时重新设置同名、同路径、同安全属性的 Cookie，值保持当前 token；Max-Age 按实际返回过期时间减去响应时服务端当前时间计算，向下取整。数据库提交成功后才产生成功响应，不把 token 放入 JSON。响应设置 `Cache-Control: no-store`。

失败语义：

- 无 Cookie、未知 token、会话到期或撤销、账号停用或删除：401，沿用 `not_authenticated`。
- Origin 不允许：沿用现有 403，不将其解释为登录失效。
- 数据库或服务暂时故障：5xx，不伪装成 401；前端不清除登录状态。
- 失败不发送续期 Cookie，也不主动清除 Cookie，避免并发响应误清除刚建立的新登录。

普通业务接口、`GET /auth/me`、SSE 和 Worker 均不隐式续期。后端无法证明请求是否出自真人操作，主动/后台区分由受控前端调用约定实现，不将其作为安全授权边界。

## 4. 数据与事务建议

### 4.1 保存固定续期窗口

在 `AuthSession` 和 `auth_sessions` 增加 `renewal_window_seconds`，只允许 604800 或 2592000。新会话按注册/登录时的选择写入；续期不改变该值。

这是会话自己的期限策略，不从续期后的 `expires_at - created_at` 推断，也不新增绝对过期时间。继续保存原 token 摘要；本期不轮换 token，避免多标签页并发导致凭据互相失效。

### 4.2 原子续期

仓储新增续期能力，在单一事务内完成以下步骤：

1. 按 token 摘要只读定位所属用户和会话；未找到则失败。
2. 按既有顺序锁 users 行，再锁对应 auth_sessions 行；重新确认归属和 token 摘要，不能依赖步骤 1 的有效性快照。
3. 获锁后读取当前 UTC 时间，再检查用户 active、未删除、会话未撤销且 `expires_at > now`；恰好到期也失败。不能使用等待锁之前的时间恢复已经到期的会话。
4. 将有效期更新为 `max(原 expires_at, now + renewal_window_seconds)`，提交后返回实际有效期。

锁后时钟应可注入测试；共享日期处理优先复用 `backend/src/common/date.py`。领域端口只暴露类型化结果，HTTP Cookie 处理留在 API 层。

### 4.3 并发与撤销

- 多标签页偶发并发续期允许全部成功，数据库有效期只增不减。
- 登出先提交撤销：后续续期失败。续期先提交：随后登出仍能撤销，不存在续期清除撤销标记的路径。
- 即使续期成功响应晚于登出响应到达，使浏览器重新保存旧 Cookie，该 token 也已经在服务端撤销，不能重新登录。
- 修改密码撤销其他会话时，与续期遵循统一锁顺序；被撤销的会话不得复活，当前保留会话继续按自身窗口续期。
- 账号停用/删除与续期按用户行锁协调；状态变更提交后，会话不能继续用于认证或续期。
- 并发响应乱序可能让浏览器 Cookie 期限略早于数据库期限；数据库有效期始终为授权依据。前端尽量合并续期请求，本期不承诺跨标签页网络请求严格全局单次。

本期不扩展修改密码、登录已有竞态的修复范围；若实施发现这些行为阻碍上述续期保证，应先报告并明确相关修复范围。

## 5. 前端接入契约

### 5.1 活跃事件与节流

在明确由用户操作启动的业务请求入口调用续期调度器，不能统一拦截所有 HTTP 请求后自动续期，也不能通过定时器持续续期。

- 包括用户手动导航和刷新后产生的首次页面数据加载；同一次导航的批量加载合并。
- 排除定时刷新、预加载、自动重试、SSE 重连和后台任务状态查询。
- 不以鼠标移动、页面可见、单纯输入或滚动作为本期续期信号；未发送输入仍按失败规则保留。
- 没有成功续期记录时，下次主动操作可立即尝试；成功后 5 分钟内的主动操作不再续期，不安排无人操作时的补发。
- 同一标签页只保留一个进行中的续期请求。业务请求不等待该请求。
- 失败不推进最近成功时间；临时失败只在后续主动操作重试。可设置短暂重试冷却，避免一次批量操作引发请求风暴；不自动后台重试。

### 5.2 标签页与登录切换

建议使用 BroadcastChannel 广播续期成功、退出和登录切换事件；必要时使用不含 token 的存储事件作为兼容方式。Cookie 继续为唯一认证凭据，不把 token 放到 localStorage。

跨标签页共享最近成功续期时间以减少重复请求；前端使用单调时间处理本标签页节流，跨标签页时间只用于优化，不能改变后端有效性判定。并发少量重复请求必须由后端正确处理。

退出后立即停止本地调度并通知其他标签页。登录切换时重置节流状态，并使用本地登录代次忽略旧请求结果，避免旧续期的 401 把新登录踢出。即使消息通道不可用，所有标签页后续请求仍由服务端认证保证退出生效；不承诺每个标签页 UI 都瞬时更新。

### 5.3 失败与输入保留

只有当前登录代次的明确 401 才进入需登录状态；网络错误、5xx、403 不触发自动退出。保留页面内未发送内容并展示登录提示；不得为了续期失败直接刷新页面丢弃输入。

本期只要求页面内存中的草稿在重新认证流程中保留，不新增跨刷新、跨设备草稿持久化。前端实现时需选择不会卸载并丢弃草稿的登录交互方式。

## 6. 迁移与兼容建议

历史固定期限会话可以从未被续期的 `expires_at - created_at` 识别原 7 天/30 天策略。迁移时：

1. 新增可空窗口字段，检查历史数据；精确匹配 7 天/30 天的记录回填相应窗口。
2. 异常期限不能静默推断或延长：迁移预检报告并中止，由维护者确认处理后重跑。
3. 回填后加 NOT NULL 与允许值约束；迁移不修改现有过期时间和撤销时间，过期会话仍过期。

建议采用维护窗口，暂停认证写入后迁移并统一更新应用，避免旧版本插入没有窗口字段的新记录。启用续期后，不能再用创建时间与过期时间差推断策略；降级会丢失已保存的策略，需停止续期并重新评估，不能将降级视作无损操作。

迁移文件编号以实施时实际 Alembic head 为准，不预占当前工作树中其他功能的编号。

## 8. 验收条件

1. 注册和普通登录使用 7 天窗口，“记住我”使用 30 天；续期后窗口不变。
2. 有效会话续期后，数据库和响应 Cookie 都延长，token 值不变；持续续期可超过原登录后的 30/90 天。
3. 到期边界 `expires_at == now`、撤销、账号停用或删除均返回 401，不写过期时间、不签发 Cookie。
4. 普通业务请求、`/auth/me`、后台轮询、SSE 重连及 Worker 不改变会话过期时间。
5. 前端连续主动操作在成功后 5 分钟内不重复续期；无主动操作时不发续期请求。第 5 分钟后的下一次主动操作触发续期。
6. 网络/5xx 失败保留登录和未发送内容，下次主动操作重试；明确 401 提示登录；403 不当作退出。
7. PostgreSQL 并发测试覆盖重复续期、续期与登出、续期与密码撤销；最终撤销状态不被覆盖，有效期不回退。
8. PostgreSQL 测试覆盖锁等待跨越过期时刻：获锁后必须拒绝已经过期的会话。
9. 同一 Cookie 的标签页共享续期；任一标签页退出后其他标签页请求认证失败；独立设备 B 不因设备 A 活跃而续期。
10. 延迟返回的旧请求不会改变新登录的前端状态；退出后的晚到 Cookie 不能恢复服务端认证。
11. 迁移正确回填两类历史会话，保留撤销/过期状态；遇异常期限中止并报告；新记录满足约束。
12. 回归注册、登录、退出、修改密码、Origin 校验、管理员认证。实施时执行项目要求的静态检查和必要测试，不以 SQLite 测试替代真实 PostgreSQL 并发验证。
