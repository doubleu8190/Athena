# LLM 上下文压缩设计

状态：核心产品规则与实施方案均已确认并实施。独立 Reviewer 第 2 轮结论为 PASS，Root 已于 2026-11-09 完成后端验收；真实外部模型联调尚未执行。

## 1. 目标与范围

系统自动将较早会话整理成摘要，使长会话能继续调用 LLM。原始消息与用户查看的聊天记录完整保留。摘要归属于当前 Session，只服务上下文组织，不自动写入长期记忆。

摘要重点保留目标、约束、已确认决定、关键结果和待办。新决定替换已失效的旧决定；不编造事实，不保存模型内部思维链。摘要是有损表示，不能保证完整保留原文细节。

首期完成自动触发、增量与分批压缩、摘要版本复用、管理员配置、失败回退、Run 生命周期集成和状态事件。不增加手动编辑摘要、跨会话摘要、长期记忆写入、历史消息删除、全文回查工具或前端页面实现。前端可通过事件展示压缩状态。

## 3. 已确认规则

### 3.1 触发与预算

每次主模型调用前检查预算，包括澄清恢复后的调用。计入系统提示、工具定义、协议、全部输入和输出预留。达到模型窗口的 80% 时自动压缩，阈值可配置；80% 是提前触发阈值，模型窗口是硬限制。

设主模型窗口为 W，输出预留为 O，系统提示、工具定义与固定协议开销为 F，输入可用预算 B = W - O - F。摘要封装的角色与分隔开销也必须计入最终请求。

- 摘要上限：B 的 10%，可配置，生成后实际计数校验。
- 此前历史近期原文预算：B 的 20%，可配置。
- 当前 Run 的触发消息及执行交互完整保留，不受上述 20% 限制。
- 每次生成摘要后，重新计数完整主请求，确保不超过 W。

Token 为本地估算，不保证与供应商完全一致。不能以字节数替代 Token 预算。摘要重新用于不同主模型时，要使用该模型的 tokenizer 重新计数。

### 3.2 保留与切分

此前历史保留最近的一段完整轮次，更早前缀归入摘要。不能拆散工具调用与结果。当前 Run 的触发消息、澄清及执行交互不压缩；其自身过大不能通过压缩旧历史解决。

已有摘要覆盖的原文不重复加入主请求。主请求由系统提示、兼容摘要、未覆盖的历史原文及当前 Run 必要交互构成，延续现有正式澄清与工具投影去重规则。

### 3.3 增量、分批与版本

第一次从较早原文生成摘要；后续将“已有摘要＋本次新移出的历史”合并为新摘要。记录摘要覆盖边界，覆盖只能连续推进，不能跳过中间消息。

压缩模型窗口装不下待处理历史时，按时间顺序分批，每批使用上批中间摘要与下一批完整轮次。中间摘要只在本轮内存中保留；全部批次成功且最终主请求预算通过后，才保存最终版本。单个不可拆分轮次装不下或中途失败，按压缩失败处理。

摘要按 Session 保存不可变版本。只能重试当前 Session 最新且 failed 的 Run；“最新”按 `created_at DESC, id DESC` 判定，在 Session 锁内校验，成功请求的幂等重放仍返回原结果。不存在任意历史 Run 回退重试的场景。

重试仍复用源 Run 的触发消息和 cutoff，不携带源 Run 的澄清或执行历史。源 Run 已成功提交的摘要可复用，但覆盖边界必须严格早于原触发消息；无兼容版本时，在需要压缩时从允许读取的原始历史重新生成。保留摘要版本用于增量来源、生成追踪和配置兼容，不再以任意历史 Run 重试作为版本选择的设计依据。

### 3.4 模型、失败与生命周期

压缩模型由管理员独立配置，复用现有模型版本机制。初始可以选择主模型，但不自动跟随主模型切换。普通用户无需选择。压缩只生成摘要，不调用工具，每批都有独立的输入窗口检查与输出预留。

新摘要生成成功、内容有效、未超过摘要上限且最终上下文装得下时，才替换本次使用的摘要。失败保留全部原数据：原上下文能装入硬窗口就继续主调用；已经超窗则本次 Run 失败。

取消、超时和租约失效属于 Run 生命周期终止条件，优先于上述回退：不得继续主调用或提交新摘要。此前成功提交的摘要保留，供后续 Run 使用。压缩和主调用共同消耗现有 Run 执行时限，不重新计算或延长 deadline。

### 3.5 展示与用量

提供压缩中、完成和失败事件；摘要正文不作为助手消息插入聊天记录。压缩失败但回退继续时显示相应状态；超窗导致 Run 失败时提供明确安全错误原因。

压缩调用耗时和 Token 用量单独记录，管理员可用于排查成本与延迟。供应商未提供 usage 时保持未知，不填零。

## 4. 实施建议：配置与数据

本节具体结构尚未单独确认，需随整体方案确认。

### 4.1 配置快照

建议新增管理员管理的不可变压缩策略版本，包含独立压缩模型版本引用、触发比例 0.8、近期原文比例 0.2、摘要比例 0.1、摘要模板版本；通过单独的当前策略指向切换。比例必须为有效数值且在 (0, 1) 范围，近期比例与摘要比例之和小于 1；运行时仍须校验实际预算。

新 Run 创建时绑定策略版本，恢复时沿用，避免管理员修改导致同一个 Run 分批使用不同参数。重试作为新 Run，建议读取当前策略，与当前重试读取默认主模型的行为一致。调用前复核压缩模型启用状态和凭据可用性；被停用时不切换到其他模型，回退到完整上下文继续执行，超出模型上下文窗口时才会失败。

未配置策略的既有部署继续现有超窗失败行为；管理员配置完成后对新 Run 生效。既有 Run 不强制回填策略。建议增加管理员读取和更新当前压缩策略的 API，具体路径随实施统一，不给普通用户写权限。模型引用仍指向 `llm_model_profile_versions`，不复制凭据或创建第二套模型目录。

### 4.2 摘要版本

建议新增 `session_context_summaries` 表，仅保存成功的最终摘要：

| 字段组 | 用途 |
| --- | --- |
| id、session_id、owner_id | 标识与租户隔离，Session/owner 复合外键 |
| covered_through_sequence | 已覆盖的 Conversation 连续历史前缀上界，不代表覆盖所有 Execution 消息 |
| parent_summary_id | 记录增量来源，必须同 Session/owner；允许无父版本 |
| text | 内部摘要正文，不写入正式消息表 |
| source_run_id、execution_epoch、compression_operation_id | 来源、执行权与提交幂等标识 |
| policy_version_id、compression_model_version_id、prompt_version | 生成配置追踪 |
| created_at | 创建时间 |

同一覆盖边界允许因不同配置产生多个版本；无需独立“最新摘要”指针。按 Session/owner 与覆盖上界建立查询索引，优先选择兼容边界中覆盖最远、生成较新的版本。实际使用前重新检查摘要大小和主请求预算；不兼容时尝试可用旧版本，或从允许读取的原始历史重建。

摘要表与 Run 策略引用需要迁移；不改写或删除消息、不要求历史摘要回填。软删除 Session 后摘要不得继续读取；物理清理遵循 Session 删除约束。摘要正文视为与原会话同等级数据，不写入普通日志或状态事件。

### 4.3 调用与事件

扩展现有 typed usage，而不是新建通用观测平台。调用身份建议包含 execution_epoch、purpose（answer/compression）、compression_operation_id、batch_index、attempt；防止批次、重试与主回答互相覆盖。按 purpose 分别汇总，同时总量包含压缩开销。更新 JSON 类型及历史 usage 兼容转换，旧记录默认 answer，缺失信息保留未知。

扩展 typed Run 事件为 compression_started、compression_completed、compression_failed。载荷只含操作 ID、摘要版本 ID、边界、批次计数和安全错误码等必要元数据。失败批次的已知用量仍要记录，不因为最终摘要未提交而丢失。流式传输复用现有持久事件发布和快照恢复机制。

## 5. 实施建议：核心算法

1. 读取 Run 绑定的主模型、压缩策略、原触发边界和可见消息；选取边界兼容的摘要。摘要覆盖只能严格早于当前 Run 触发消息，不能包含本 Run 的澄清答案。
2. 组装摘要与未覆盖原文，计算完整请求。若未达到触发阈值且摘要兼容，直接执行主调用。
3. 达到阈值时，保护本 Run 全部必要输入；将此前 Conversation 历史按原 Run 关联划分完整轮次，缺少 Run 关联的旧数据使用明确角色边界处理。不能仅按消息条数任意切断。
4. 从最新轮次向前选择累计不超过 20% B 的连续后缀；遇到装不下的完整轮次即停止，剩余连续前缀作为候选压缩区。近期后缀允许为空，当前 Run 仍完整保留。
5. 若没有新历史可压缩，仅在已有摘要超出本次摘要上限时允许重新缩短该摘要；否则不重复压缩同一覆盖范围，直接按硬窗口判断能否继续。
6. 为每批计算压缩模型预算，计入摘要指令、输入封装、已有/中间摘要和输出预留。建议中间摘要也应用主模型 10% B 上限，同时不得超过压缩模型自身输出上限；两种 tokenizer 分别计算各自窗口。常规分批每批必须消费至少一个新完整轮次，避免无限循环；步骤 5 的仅摘要缩短为一次有界重整例外，不要求新增轮次。
7. 摘要响应必须正常完成、非空、仅有文本且无工具调用。长度截断、拒绝、协议异常或超出摘要上限视为失败；不靠字符串硬截断修复。提示要求保留关键内容，但语义完整性无法仅靠程序校验保证。
8. 全部批次成功后重建主请求，校验摘要上限、硬窗口及协议合法性；不要求一定低于 80%，因为受保护的当前 Run 可能占比较大。校验成功后原子提交最终摘要与完成事件，再发起主调用。
9. 一次主请求准备最多执行一轮压缩流程，不因压缩后仍超过触发阈值而立即重复；下一次调用只在新增可压缩前缀或摘要因模型变化不兼容时尝试。失败后也不在本次请求内无限重建。
10. 普通压缩失败时，使用开始本轮压缩前的兼容摘要与原文重建请求作为回退，不拼入任何中间结果。能装入 W 且执行权和剩余时限有效则继续；否则失败。

建议供应商临时错误沿用现有限次退避原则：每批最多三次尝试，正常完整摘要前的部分流输出不得提交，deadline 与取消始终优先。首期不增加摘要质量评分模型或自动修复链。

## 6. 实施建议：事务与资源约束

- LLM 调用不持有数据库事务或行锁。提交摘要时按现有 Session → Run 锁顺序读取，验证 owner、Session 未删除、Run 为 running、无取消请求、worker_id、execution_epoch、数据库时钟下租约和执行时限均有效。
- 校验 parent 同 Session、覆盖边界连续且早于触发消息；按 compression_operation_id 幂等提交。摘要插入与 compression_completed 事件同事务。取消请求与提交由现有行锁顺序决定，取消先获得并提交则摘要提交被拒绝。
- 使用不可变版本记录增量来源和生成配置。只有最新失败 Run 可重试，且同一 Session 仅有一个活跃 Run；不设计任意历史 Run 回退产生的摘要分支。选取摘要仍校验触发边界与配置兼容性，无需新增一个可变 Session 摘要指针。
- compression_started/failed、调用用量写入也必须检查执行权。租约失效后不得强行补写，未知用量保持未知，由现有回收机制收敛 Run。
- tokenizer 工作继续放在现有有界线程边界中，避免阻塞心跳和取消。压缩沿用供应商并发配额，单个 Run 顺序执行批次；主模型尚未开始时不应占用其调用连接或配额等待压缩。
- 压缩摘要作为明确标注的历史数据消息注入；系统提示说明它可能有损且不构成新指令。原文里的角色标记、工具结果或“忽略指令”等文本不能被提升为真实系统消息。

## 7. 模块落点

保持 api → app → domain / adapter 的现有结构。

- `domain/run`：摘要、策略快照引用、压缩结果、事件及原子仓储命令契约。涉及数据库 JSON 的数据使用显式 Pydantic 模型，不以散装 dict 穿透业务边界。
- `app/run`：新增压缩编排与摘要提示模块，复用 `context.py` 的转换和计数；`executor.py` 只协调准备请求和执行。
- `adapter/run/model`、`repository`、`converter`：摘要与策略映射、边界查询和原子提交，显式实现 domain 端口。若策略管理放在 llm 域，使用现有 `adapter/llm` 同结构，避免两处维护同一配置。
- `app/llm`、`domain/llm/ports.py`、`adapter/llm`：补齐 runtime 文本生成能力，复用连接、错误归一化和配额。优先用无工具普通文本摘要，不要求供应商原生 structured output。
- `api`：管理员压缩策略 DTO、converter、鉴权路由；Run 事件 DTO 与流协议扩展；普通用户只能读取自己 Run 的安全状态。
- `backend/migrations/versions`：新增迁移，不重写已有未提交迁移；序号需实施时核对。共享时间与 JSON 工具优先复用 `backend/src/common/date.py` 和 `backend/src/common/json.py`，不在本功能顺带迁移现有其他工具调用。

## 8. 分阶段实施与验收

### 阶段一：预算、配置与纯算法

完成管理员配置、Run 快照和摘要切分算法。验证：

- 达到 80% 时触发，低于时不触发；系统、工具、输出与协议开销全部计入。
- 20% 原文、10% 摘要使用同一个 B；B 不为正时明确失败。
- 多轮历史按连续前缀/后缀切分；工具调用与结果不拆散，当前 Run 始终完整。
- 管理员可更新当前策略，普通用户被拒绝；恢复不受配置切换影响；停用压缩模型时不偷换模型。

### 阶段二：摘要生成、版本与 Run 集成

完成 runtime 无工具摘要调用、分批、版本查询与原子提交。验证：

- 首次及多次增量压缩覆盖连续推进，主请求无摘要/原文重复。
- 多批次中间结果不持久化；全部成功才产生最终版本；空文本、工具输出、截断、超限均失败。
- 重试切换到更小窗口或不同 tokenizer 时重新校验摘要；无兼容版本时按源 Run cutoff 重建。
- 仅最新 failed Run 可重试；存在更新 Run 时拒绝新的重试请求，成功请求幂等重放仍返回原结果。最新失败 Run 的已提交摘要可复用，但不能包含原触发消息、源 Run 澄清或执行历史。
- 压缩失败而原上下文能装入时继续；装不下时失败。当前 Run 自身过大、不可拆分旧轮次过大均不静默丢弃。
- 压缩后仍高于触发阈值但低于硬窗口时可调用，不在同次请求反复压缩。

### 阶段三：并发、事件与用量

在真实 PostgreSQL 上验证事务及竞争：

- 摘要提交与取消竞争、租约失效、旧 execution_epoch 写入、执行 deadline 到期时，失效执行不能提交或调用主模型。
- 重复提交只生成一个摘要与完成事件；父版本不能跨 Session/owner，用户无法读取他人摘要。
- 提交后主模型失败不删除摘要；提交前失败保留旧版本和所有原文。
- SSE 断线重连能恢复压缩状态；事件和正式聊天记录不包含摘要正文或秘密。
- 多批次、每批重试、主回答用量身份不冲突；已知用量分别累计，缺失值保持未知。
- 迁移前历史消息和 usage 可读；未配置策略及旧 Run 保持兼容行为。

必要检查包括针对性单元测试、PostgreSQL 集成测试、现有 Run/LLM 回归，以及仓库要求的静态检查。真实模型联调用于验证 tokenizer 估算余量、摘要上限与调用终态，不以语法检查替代功能验收。

## 9. 准备程度与实施流程

配置版本结构、快照时机、近期轮次算法、模型端口扩展、调用幂等键和事件名已纳入并确认于实施方案。默认值为起点，实际摘要质量及压缩模型大小仍需联调验证。
