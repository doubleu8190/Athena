# 知识库设计（待确认）

状态：Root 设计草案，尚未确认，未实施代码。本文中的范围、接口和数据结构均为建议。

## 1. 当前基础与目标

当前代码已有用户认证、用户私有项目、Session 和两类消息持久化；尚无文件模块、
后台任务、模型调用、Run 编排或知识检索。消息的 `FileRefPart` 仅保存文件引用，
不代表文件上传、存储和下载已经实现。

沿用模块化单体和 `domain/app/adapter/api` 边界。知识库负责资料解析、索引、
检索和来源定位；文件模块负责原始文件及下载；记忆模块负责跨会话信息。
聊天附件不会自动成为知识，聊天内容也不会自动写入知识库。

首版目标：用户能创建知识库，导入资料，看到处理结果，测试检索，并打开结果的
来源片段。后续接入 Agent 时，回答能引用实际检索到的资料。

## 2. 产品范围建议

首版提供：

- 用户私有知识库：名称、说明、创建、查询、修改和删除。
- 手动文本，以及 UTF-8 TXT、Markdown、带文本层 PDF 导入。
- 文档列表、处理状态、失败原因、失败重试、替换内容和删除。
- 检索测试：输入问题，查看片段、来源、定位和检索降级提示。
- 项目关联知识库，同一知识库可供同一用户的多个项目使用。

首版后置：共享库、组织权限、网页抓取、定时同步、OCR、图片理解、复杂表格、
Office 文件、知识图谱和自动知识抽取。扫描 PDF 明确提示不支持，不生成空索引。
不依赖这些后置能力完成首版闭环。

## 3. 归属与项目关联

知识库归属于用户，不从属于单个项目；文档只属于一个知识库。
`project_knowledge_bases` 保存同一 owner 内的多对多关联。

- 所有 owner 由已验证的登录上下文注入，不接受模型或客户端自报。
- 列表、文档、任务、搜索、片段与原文下载都检查当前用户权限。
- 跨用户资源统一按不存在返回 `404`；数据库复合外键约束 owner 一致。
- 创建项目关联与项目删除使用相同的项目行锁边界；删除项目时只删除关联，
  不删除知识库，也不改变现有 Session 删除约束。
- 删除知识库时原子标记不可见并移除项目关联；重复删除保持幂等。

未来项目会话默认使用项目当前关联的知识库；无项目会话默认不检索知识库。
显式选择其他本人知识库可在后续对话入口设计，首版不另加 Session 关联表。

## 4. 用户操作与页面

建议提供三个入口：

| 入口 | 主要内容 |
| --- | --- |
| 知识库列表 | 名称、说明、文档数、进入和删除 |
| 知识库详情 | 文档列表、导入、状态、替换、重试、删除及检索测试 |
| 项目设置 | 关联或移除本人知识库 |

文档详情显示当前生效版本与正在处理的更新。旧版本仍可检索时应明确展示，
不能只用一个“处理中”覆盖真实状态。失败原因使用可操作的安全错误码与说明，
不返回内部路径、堆栈或供应商凭据。

## 5. 文件与导入链路

```text
上传到文件模块 / 提交文本
  → 校验归属、类型、大小和配额
  → 创建文档、待处理版本及持久化任务
  → 提取文本和来源定位
  → 按段落与标题切分
  → 生成关键词索引及向量
  → 校验完整性
  → 原子发布新版本
```

上传文件必须是当前用户拥有、上传完成且未删除的文件。知识库服务通过文件模块
公共接口读取，不能通过客户端路径读取宿主机文件。文件名和 MIME 不能作为
唯一类型依据；解析设定时间、内存、页数与提取文本长度限制。

手动文本同样走版本与索引流程，原始文本保存在版本记录中。文件文档的原文由
`source_file_id` 引用，不再复制一份二进制。文件模块须保护仍被版本引用的文件，
清理版本后再允许回收；下载始终重新授权。

建议初始限制：单文件 20 MiB、PDF 500 页、单次导入 20 份、单用户并发处理 2 份；
单用户存储与索引总量另设可配置硬上限。以上为待确认的产品默认值，不是性能承诺。

## 6. 版本、后台任务与一致性

文档是稳定身份，版本是某次内容及处理配置的不可变结果。文档保存
`active_version_id` 和 `pending_version_id`，最多一个待处理版本。
再次替换时返回冲突，用户需等待当前更新结束，首版不提供并行替换。

版本状态：`queued → processing → ready | failed`。失败可重试；重试沿用
版本身份并清理其未发布索引。首次导入失败时文档不可检索；替换失败时保留旧
生效版本。文档标题作为目录属性独立修改，不因此触发重新切分。

建议首版使用 PostgreSQL 持久化任务及独立 worker 进程，不另引入消息中间件。
该建议新增后台执行能力，需要用户确认；不能使用响应结束后的内存任务代替。

- 创建版本与任务同事务提交，避免已有文档却丢失处理任务。
- worker 用任务行认领、租约和心跳处理进程崩溃；重领增加 fencing token。
- 每次写入及发布检查 token、租约、待处理版本和文档可见性；旧 worker 结果拒绝提交。
- 外部解析和模型请求在数据库事务外执行，不持有长事务等待网络。
- 片段以 `(version_id, ordinal)` 唯一；重复任务不能产生重复片段或重复发布。
- 索引完整后，在文档行锁内切换 active 指针并清空 pending；失败不切换。
- 删除与发布锁定同一文档，删除后正在执行的任务不能发布或重新激活。
- 失败重试有次数上限、退避及错误分类；确定性格式错误不自动反复重试。

删除立即阻止后续新检索与下载，物理清理由可重试任务异步执行。已返回客户端
或已交给模型的内容无法撤回；后续 Run 接入需定义删除后的中止或继续语义。
首版建议在发送模型请求前重新检查证据可见性，失效证据剔除，不把权限快照当授权。

## 7. 检索设计

检索用例只返回证据，不生成答案。输入为 query、已授权的知识库集合与返回数量；
输出包含片段 ID、文档及版本 ID、标题、原文片段、定位和实际使用的检索通道。

建议采用关键词与向量两路召回、按排名融合、去重与相邻片段合并，最后按片段数
和上下文预算截断。首版不增加独立重排模型或查询改写模型。

关键规则：

1. 先将 owner、允许的知识库、未删除文档及 active version 限定为候选集合，
   再在各通道取 Top-K；禁止先全库取 Top-K 再过滤权限。
2. 关键词通道需覆盖中文词句、专有名词、编号和代码；不能未经验证直接采用
   默认英文分词配置。中文索引方案必须用真实中文样例验收。
3. 向量通道负责语义近似；保存模型标识、维度与处理配置版本。查询模型必须
   匹配当前索引，首版固定一个 embedding 配置，变更需受控重建后统一切换。
4. 通道分数不直接相加；融合名次只用于排序，不展示为“答案可信度”。
5. 单路临时不可用时允许另一通道返回，并标记降级；两路均不可用返回服务错误，
   不能伪装成“未找到”。导入时 embedding 不可用则保持待重试或失败，不假报 ready。
6. 查询数量、长度与返回预算有上限；空结果明确返回未命中，不由检索层编造答案。

元数据和任务沿用 PostgreSQL。向量存储、中文关键词实现与 embedding 提供方
尚未选定；需核对部署环境、中文检索表现、外发数据边界与成本后确认，不在
本草案中假定已有向量扩展或模型服务。首版预期不额外引入独立搜索集群。

## 8. 来源与未来 Agent 接入

每个片段保存对解析文本的字符区间；PDF 额外保存页码，Markdown 保存标题路径。
TXT 和手动文本保存行号。切分不能制造虚假页码，跨页片段需保存页码区间。

检索结果用于构造服务端签发的证据编号。模型只引用本次实际返回的编号，服务端
解析并验证引用，再映射到文档、版本及片段。历史引用绑定具体版本，不能随着
文档更新静默跳到新内容；旧版本保留用于引用，但不参与普通检索。
删除后引用显示“来源已删除”，不会继续返回旧片段正文。旧消息正文保持历史内容。

当前消息只有 text、file_ref、tool_call、tool_result，没有专门引用类型。
未来接入时需单独扩展类型化 citation 结构及序列化，不把结构化引用塞进随意字典。

现有 MCP 草案明确首版不提供内置工具。本轮因此只设计应用服务和检索测试 API，
不注册模型可见的 `knowledge_search`。未来可选择：

- Run 调用模型前做检索，将有引用的证据加入上下文；或
- 经用户确认增加原生知识检索工具，接入统一工具网关。

两者先选一个完成闭环，不同时建设两套入口。检索内容按资料处理，不作为系统
指令，也不授予执行权限；Subagent 的检索范围不得超过当前任务授权范围。

## 9. 最小数据模型建议

| 表 | 主要字段与用途 |
| --- | --- |
| `knowledge_bases` | id、owner_id、name、description、时间与 deleted_time |
| `project_knowledge_bases` | owner_id、project_id、knowledge_base_id；关联唯一 |
| `knowledge_documents` | id、owner_id、knowledge_base_id、title、active_version_id、pending_version_id、时间与 deleted_time |
| `knowledge_document_versions` | id、document_id、owner_id、source_kind、source_file_id 或 source_text、content_hash、处理配置、状态、error_code、时间 |
| `knowledge_chunks` | id、version_id、ordinal、text、类型化 locator、关键词索引及向量存储所需引用 |
| `knowledge_ingestion_jobs` | id、version_id、status、attempt、lease_until、fencing_token、next_attempt_at、error_code、时间 |

处理配置、locator 使用显式类型及序列化边界，避免不受约束 JSON。
版本 source 二选一由约束保证；active/pending 指针必须引用同一文档版本。
跨 owner 关系由复合外键保证；片段权限从所属版本、文档和知识库链路校验。
新资源使用带业务前缀的 UUID，不复用项目现有的进程内时间 ID。

content_hash 用于完整性和同一文档重复提交的 no-op 判断，不跨用户去重，
也不阻止用户有意上传两个相同文件。创建与替换接受 owner 内的幂等键，
相同键及相同请求返回已有结果，不同请求复用同一键返回冲突。

## 10. HTTP 与代码边界建议

```text
POST/GET           /api/v1/knowledge-bases
GET/PATCH/DELETE   /api/v1/knowledge-bases/{kb_id}
POST/GET           /api/v1/knowledge-bases/{kb_id}/documents
GET/PATCH/DELETE   /api/v1/knowledge-bases/{kb_id}/documents/{document_id}
POST               /api/v1/knowledge-bases/{kb_id}/documents/{document_id}/versions
POST               /api/v1/knowledge-bases/{kb_id}/documents/{document_id}/retry
POST               /api/v1/knowledge-bases/{kb_id}/search
GET                /api/v1/knowledge-bases/{kb_id}/chunks/{chunk_id}
GET                /api/v1/projects/{project_id}/knowledge-bases
PUT/DELETE         /api/v1/projects/{project_id}/knowledge-bases/{kb_id}
```

导入与替换返回 `202`，包含文档和版本状态，客户端通过详情轮询；首版无需 SSE。
PATCH 文档只修改标题；替换另走 versions 接口。检索测试无须依赖 Session 或 Run。
新增写接口沿用登录 Cookie、同源检查和严格请求字段校验。

拟新增 `domain/knowledge`、`app/knowledge`、`adapter/knowledge` 和知识 API/DTO；
parser、embedding、检索存储与原文读取在端口外实现。复用既有数据库和认证，
不创建通用 RAG 框架、微服务或另一套用户体系。文件与 worker 是明确的前置
能力，按真实用例落地，不用空接口假装完成。

## 11. 实施顺序与验收

1. 确认产品范围与技术依赖；补齐最小文件能力、知识目录与项目关联。
2. 完成持久化任务、解析、版本发布及失败重试。
3. 完成中文关键词与向量检索、检索测试和来源查看。
4. Run 与模型链路就绪后，另行确认 Agent 接入及引用消息协议。

前三阶段即可独立验收知识库，不把尚未实现的对话链路列为已完成。

必须验证：

- 两用户同名知识库互不可见；伪造项目、文件、任务或片段 ID 均不能越权。
- 无关用户的高相似内容不挤占本人的 Top-K；项目仅使用有效关联的库。
- 中文问题、语义改写、精确编号和无答案样例均有固定测试集及预期来源。
  实施前确定 Hit@K 目标与无命中判定，记录查询延迟，不预设未经测量的 SLA。
- 导入后可检索并打开原文定位；空文件、扫描 PDF、超限文件返回明确结果。
- 替换期间仍能查旧内容；失败不影响旧版；发布后普通检索只查新版。
- 重复提交、重复认领、崩溃重启及旧 worker 迟到不会产生重复或覆盖新版。
- 删除与任务发布并发时资料不会复活；项目删除与绑定并发时不残留有效关联。
- 单路检索失败显示降级；全部失败显示错误；模型配置不匹配时拒绝静默混用。
- 真实 PostgreSQL 临时 schema 测试覆盖迁移、复合外键、任务竞争及原子发布；
  假 embedding 只能证明流程，仍需真实中文 embedding 样例验证检索效果。

## 12. 确认项

建议先确认三个产品决定，再补足可实施的技术选型：

1. 用户私有知识库独立存在，可被同一用户多个项目复用。
2. 首版只含文本、TXT、Markdown、文本 PDF，不含 OCR、网页同步和共享。
3. 首先完成知识管理与检索测试；Agent 接入后续单独确认，保持现有无内置工具决策。

实施前还需确认文件存储、后台 worker 部署、中文索引、向量存储、embedding
提供方及数据外发许可，以及配额。用户确认方案后，按仓库约定交给 Implementer
实施，之后由 Reviewer 独立审查，Root 最终验收。
