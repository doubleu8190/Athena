# 记忆功能实施方案

历史核心建设方案。当前增量实施以 [记忆全生命周期实施方案](memory-lifecycle-implementation-plan.md) 为准；
下文“不预建”约束不适用于已授权的生命周期增量。

本方案仅细化设计，不授权代码修改。依据 [memory-design.md](memory-design.md)。
记忆是现有后端中的业务模块，共用应用、数据库、连接池、配置、迁移和生命周期。

## 1. 首版范围

先实现add、recall和必要管理能力：新增、修改、确认候选、列表、删除、设置。
混合召回保持关键词+向量检索、RRF融合、重排、预算和返回前复核。
保留用户/项目范围隔离、来源引用、版本冲突及正文/向量原子写入。

不预建：范围状态表、来源失效表、操作流水表、任务队列、清除代次、后台任务
恢复、删除协调状态机、多模型切换或独立服务。自动提取、自然语言记忆意图和
前端确认界面等实际接入时再设计，默认开启的设置不代表已运行自动提取。

## 2. 代码组织

沿用现有domain/app/adapter分层，按实际代码需要创建文件：

| 位置 | 职责 |
| --- | --- |
| domain/memory | 记忆、来源、输入输出、错误及真正需要的端口 |
| app/memory | 管理用例与混合召回编排 |
| adapter/memory | ORM、转换、仓储及全文/向量查询 |
| infrastructure/memory | Embedding、重排和token计数适配 |
| main.py | 沿用现有配置、依赖组装和生命周期 |

add/recall不导入其他业务模块的ORM或私有实现。权限和范围由可信调用方提供，
共享类型及基础设施可以复用。跨模块使用现有公共接口，不预建专门协调模块。
HTTP管理及项目/聊天删除联动在核心验证后接入，不以独立部署或独立建库为目标。

## 3. 数据与迁移

先保留：

1. memories：正文、范围、状态、version、全文字段、向量、profile、
   request_id/request_hash、时间及删除标记。
2. memory_sources：记忆ID及通用来源引用，支持多个来源。
3. memory_settings：读取/提取开关，默认均开启；已有合适设置存储时直接复用。

一个version处理并发，不额外保存正文版本/向量版本。正文与向量同事务更新，
不需要异步索引版本。新增以(namespace_id, request_id)唯一约束去重，摘要
核对请求内容；不为此增加memory_operations表。删除保留无正文墓碑，使同一
新增请求重试不会恢复数据。

迁移接在实际head后；上次核对为0007，实施前重新确认。增加vector/zhparser
依赖检查、全文GIN和范围查询索引；向量先精确搜索，不提前上HNSW。
扩展由部署环境准备，降级迁移不删除共享扩展。沿用临时schema集成测试方式。

## 4. 写入流程

1. 校验可信范围和内容，读取当前version、设置，预检查request_id。
2. 释放连接，在事务外同步生成向量；检查1024维、有限数、非零。
3. 开启写事务，重新检查目标版本、删除状态、设置和新增唯一键。
4. 正文、向量、全文字段、来源一起提交；失败整体回滚。

同请求重试返回原记录，不同内容复用request_id报冲突。并发修改采用
expected_version条件更新；删除后不能自动转为新增。生成失败不保存正文。
只修改来源或过期时间无需重算；确认pending通常复用已有向量。
不在推理期间持有行锁，不用namespace设置行串行化该用户全部写入。

## 5. 混合召回

1. 校验query、范围、开关和预算；越权报错，空范围不扩大搜索。
2. 并行运行两通道，SQL取Top-K前过滤用户/范围、active、删除和过期状态。
3. 关键词采用zhparser/chinese、OR tsquery、ts_rank_cd；向量采用BGE-M3、
   1024维、余弦距离。每通道初取40条。
4. 按ID及version合并；RRF(k=60，关键词0.25/向量0.75)，取50条重排。
5. 使用bge-reranker-v2-m3重排及相关阈值过滤。失败返回明确降级状态，不能
   直接把RRF分数当成相关性阈值；未校准的降级候选不返回。
6. 去重，按默认8条/1200tokens选完整记忆，不截断条件或用无关结果凑数。
7. 最终批量复核version、状态、过期、读取设置；失效条目丢弃，允许少返回。

返回ok/degraded/disabled/unavailable，区分零命中和检索失败。日志记录耗时、
ID/版本和原因码，默认不记录查询、正文及向量。不新增召回缓存。

## 6. 配置与效果验证

参考Athena的本地Embedding和Reranker实现，模型启动预热；配置纳入现有体系。
初始向量最低接纳值0.70；候选数、权重、重排阈值均配置化。Token计数使用
固定模型revision的BGE tokenizer，明确它是模块预算单位。

沿用总召回60秒的初值，推理使用有界并发和超时，真实线程结束前不释放容量。
具体限制依据实际机器和小规模真实调用调整，不预建通用推理调度框架。

先准备覆盖中文同义表达、专名版本号、无关问题、否定条件和范围隔离的固定
样例，分开用于校准和验证。记录命中/误召回、耗时及预算，用结果调整阈值。
不把未经测量的性能数字写成产品承诺，也不先建设完整评测平台。

## 7. 必要测试与验收

- 服务/算法单测：新增与幂等、版本冲突、融合、排序、预算、降级。
- 真实PostgreSQL：vector/全文查询、范围过滤、原子提交、失败回滚及迁移。
- 并发测试：推理期间修改/删除，同一新增请求竞争，确认与删除竞争。
- 真实模型样例：向量维度、同义召回、专名召回、无关结果过滤和重排效果。
- 资源测试：超时、取消、线程晚完成与连接清理，不遗留后台写入。

SQLite不替代真实检索验收；普通单测使用替身端口，不隐式下载模型。
执行项目pytest、ruff、mypy及diff检查；未运行的真实测试如实报告。

## 8. 接入与执行顺序

核心完成后再接管理HTTP、认证范围映射和项目/聊天删除。删除项目清除项目
记忆、删聊天保留已确认记忆的产品规则保留，但不提前建立关闭scope/任务恢复
协议。利用同一应用的公共接口及必要事务实现实际一致性，接入时补对应并发
测试；未接入前不声称已经完成删除联动。

代码实施必须用户明确授权。届时Root固定范围，由luna-implementer实施，
terra-reviewer独立审查实际diff，有效问题由原Implementer修复后重审，最多3轮，
最后Root验收。实施不顺带重构其他模块或添加未来功能框架。
