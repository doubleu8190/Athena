# 普通用户个人 Skill 设计

日期：2026-11-19

状态：产品规则已逐项确认，用户随后明确授权按本文实施。前后端实现已完成，经过一轮修复后，两侧独立 Reviewer 均为 PASS；本地 Docker 已完成真实 PostgreSQL、MinIO、模型和双用户浏览器验收，未部署目标环境。下文技术建议作为本次实施基线；任何架构变更仍须重新确认。

## 1. 目标与已确认范围

普通用户可以创建仅供本人使用的个人 Skill，以 Markdown 描述工作方法、业务规则和输出要求。管理员继续管理公共 Skill 及其脚本能力。

| 项目 | 已确认规则 |
| --- | --- |
| 归属 | 个人 Skill 仅上传者本人可查看、管理和使用，不向其他用户分享 |
| 创建 | 支持在线填写名称、描述、Markdown 正文，以及导入单个 `.md` 文件 |
| 上传 | 上传控件只能选择 `.md`，后端同时校验扩展名、UTF-8 和内容；内部统一为 `SKILL.md` |
| 内容 | 禁止脚本、其他附件、脚本登记和依赖声明；允许正文包含代码示例 |
| 生效 | 保存即启用；允许手动停用 |
| 版本 | 每次成功保存产生不可变版本；新 Run 使用当前版本，已开始的 Run 保持固定版本 |
| 使用 | 模型可自动按需加载，用户也可在聊天中主动选择 |
| 权限 | 指南不增加工具权限，不绕过审批 |
| 同名 | 公共与个人 Skill 可以同名，不同用户也可以同名；按独立 ID 区分并显示来源 |
| 删除 | 从本人管理页面和新 Run 目录中移除，已有 Run 和历史记录保留对应版本 |
| 回收站 | 首期不提供；暂时停止使用应选择停用 |

首期不包含分享、公共发布、管理员审核、用户脚本、附件资源包、依赖安装及独立脚本执行机制。管理员公共 Skill 的原有导入和启用规则保持现有语义。

## 3. 用户流程与界面建议

新增普通登录用户可访问的“我的技能”页面，与管理员公共技能管理区分。

1. 列表显示本人的名称、描述、启用状态、当前版本和更新时间，支持创建、编辑、启停、删除。
2. 创建弹窗支持在线编写或导入文件。导入控件使用 `accept=".md"`、单文件选择；若支持拖放，沿用相同校验。
3. 文件导入仅填入编辑表单，不立即保存。用户可检查和修改名称、描述及正文后统一保存。
4. 保存成功后关闭编辑器、刷新本人列表和聊天可用目录，显示“已保存并启用”；不自动把新 Skill 加入当前聊天的手动选择。
5. 编辑保存发布新版本并启用；如用户需要停用，保存后执行停用。此行为与“保存即启用”一致，编辑器应明确提示。
6. 停用和删除后刷新目录；聊天中已选但失效的项目提示用户移除，不静默替换成同名公共 Skill。
7. 删除前说明“新任务将无法使用，进行中的任务和历史记录不受影响”，确认后执行。

编辑器建议首期采用普通文本区域，不引入复杂 Markdown 编辑框架。预览如提供，应沿用安全渲染方式，不执行 HTML、脚本或外链内容。

聊天选择器及模型目录增加“公共 / 个人”来源标识，所有选中、加载及执行定位继续使用 skill_id，不按名称或 slug 作为唯一身份。

## 4. 文档输入协议建议

普通用户上传的是 Markdown 文件，不必命名为 `SKILL.md`；扩展名按大小写不敏感识别 `.md`，内部规范化文件名。

建议支持两种输入：

- 带 YAML frontmatter 的现有 Skill 文档：解析 name、description，兼容现有 slug 字段；导入后由表单补齐或修改。
- 无 frontmatter 的 Markdown：正文直接进入编辑器，名称和描述由用户补齐。

示例：

```markdown
---
name: 周报整理
description: 按本周进展、问题和下周计划整理周报
---
根据用户提供的工作记录生成周报。
不要补造未提供的事实，缺失信息应明确标注。
```

个人入口采用独立的元数据允许列表，不直接放开管理员 ZIP 解析流程。出现 scripts、dependencies 等执行声明时明确拒绝，即使值为空也不静默忽略；其他不支持字段给出字段级错误。网页提交的结构化请求同样禁止额外执行字段。

建议复用现有名称 120 字符、描述 1000 字符、正文 100000 字符上限，单文件上传增加 1 MiB 字节上限。校验空正文、非法编码、控制字符和无效 frontmatter；扩展名正确不代表内容有效。MIME 类型仅作辅助，兼容浏览器将 Markdown 标为 text/plain 的情况。

不通过扫描正文中的 Python、SQL、shell 词汇判断脚本上传。代码块保留为文档内容，不写入脚本目录，不登记可执行目标，不触发依赖探测或安装。引用本地附件仅视为文本，不抓取、展开或导入资源。

## 5. 数据与版本建议

复用现有 Skill/SkillVersion 体系，不新建平行的个人 Skill 执行系统。

### 5.1 稳定身份

建议 Skill 增加：

- `scope`：public / personal。
- `owner_id`：personal 必填，public 为空；由服务端当前认证用户赋值，客户端不可指定或变更。
- `deleted_at`：个人删除时标记；管理与新 Run 目录均排除。

`created_by` 继续作为审计字段，不替代 owner_id。增加 scope/owner_id 一致性约束，并按归属建立必要索引。主键沿用项目现有 ID 生成方式。

公共 slug 保持公共范围唯一；个人 slug 在 owner 范围内唯一，允许跨用户及公共/个人重复。首期不将 slug 作为普通用户表单必填字段：缺失时由服务端生成稳定值，后续编辑不因名称修改而更换身份。

版本包哈希不能继续全局禁止重复内容，否则两个用户上传相同文档会冲突并可能暴露他人内容存在性。建议将其改为普通查询索引，幂等仍依赖 actor、操作、请求键及请求指纹，而非跨用户内容去重。

### 5.2 不可变版本与存储

每次成功保存插入 SkillVersion，并在同一数据库事务中切换 current_version_id、设置 enabled=true、递增 revision。保留原有不可变版本供历史 Run 读取。

建议由服务端把经过校验的个人文档规范化为仅含 `SKILL.md` 的内部包，复用现有私有对象存储、manifest 与版本读取。该内部格式不意味着用户获得 ZIP 上传权限。个人 manifest 的 scripts 和 dependencies 必须为空，files 只能包含 `SKILL.md`。

个人版本无运行依赖，不调用解释器环境检查；如为兼容现有结构保留 dependency_check 字段，明确使用“空需求已满足”的兼容值，不能伪装为实际执行过探测。

### 5.3 事务与失败

- 创建：校验文档 → 存储不可变对象 → 事务内创建身份及版本并启用；数据库失败不留下半个可用 Skill，对未引用对象沿用已有清理方式。
- 编辑、启停、删除：事务内重新验证 owner_id、scope、未删除状态，复用 revision 乐观并发检查及 Repository 行锁，不增加分布式锁。
- 版本写入、当前指针和启用状态一起提交。保存失败时原版本及原状态保持可用。
- 编辑与删除竞争：先完成的事务确定结果；已删除对象不得被后到保存请求恢复。
- 同一幂等键相同内容不重复创建版本。响应返回该技能当前一致的详情：当前指针、修订号、名称、描述、版本标签和正文必须属于同一当前版本；不把原操作的旧正文与新的修订号组合返回。相同键不同请求内容返回冲突；已删除后重放返回不可用，不恢复身份。
- 多标签页基于旧 revision 保存返回冲突，保留未保存的表单内容并提示重新加载，不覆盖他人或另一标签页的更新。
- 删除只标记身份，不物理清除历史版本、正文和对象；重复删除建议按幂等成功处理，已删除对象的其他管理操作返回不可用。

## 6. 权限、目录与 Run 集成

### 6.1 所有权校验

个人管理接口必须从 CurrentAuth 取得用户身份，Service 与 Repository 共同落实归属校验。普通用户不能修改公共 Skill，也不能通过猜测 skill_id/version_id 读取他人的详情、版本或正文。

普通管理查询应在 SQL 中限定 owner_id，而非全量读取后在前端过滤。越权与不存在统一返回 404，避免暴露对象存在性。个人内容不并入管理员公共管理列表；本期不新增管理员读取个人内容的产品入口。

### 6.2 目录和快照

用户可用目录 = 已启用的公共 Skill + 本人已启用且未删除的个人 Skill。管理列表另外包含本人的停用 Skill。

`public_directory()` 应调整为身份相关的可用目录能力；现有用户 GET 目录传入认证身份。公共 Skill 保留现有依赖处理，个人 Skill 不做解释器探测。

关键改动是 `build_run_skill_snapshot()` 必须接收可信 owner_id，并在现有 Run 创建事务内读取同一权限范围。不能只改 HTTP 目录，否则伪造手动选择或模型目录仍可能越权。提交、重试等所有新快照构造调用点均需更新。

显式选择他人、停用或已删除 Skill 时创建 Run 失败，不静默忽略、不创建半个 Run。前端提示刷新目录并调整选择。

快照项建议增加来源字段，旧快照缺省解释为 public。旧 Run 继续固定原 version_id；新版本、停用和删除都不回写历史快照。

恢复执行继续使用已有快照，不按当前目录重新筛掉已删除版本。用户发起“重试”会创建新 Run，沿用当前重试构造快照的机制：按当前权限和可用状态重新检查，失效的旧手动选择需要用户调整后重新提交。

子 Run 应继承父 Run 已授权的快照，或在原有能力收缩规则内取子集，不重新读取全局目录；继承发生在服务端可信路径，不接受客户端自带快照。

### 6.3 加载与脚本边界

沿用 skill_load 和现有提示上下文机制加载个人指南，模型自动选用、用户手动选择均落到同一快照。

运行时按当前已认证且拥有该 Run 的用户读取快照，不能把任意持久化 version_id 暴露成通用用户读取接口。个人管理读取须重新验证归属；历史执行读取根据可信 Run 快照及 Run 所有权授权。

个人 Skill 没有可执行脚本。即使模型构造 skill_execute 请求或正文指向 scripts/x.py，服务端也必须拒绝未登记目标，不调用 Runner。指南可以建议调用用户原本可用的工具或公共 Skill，但不能授权其他用户私有内容、任意脚本路径或提高权限。

来源标识用于可辨识性，不表示个人正文具有系统指令优先级。个人名称、描述和正文以 USER 角色的不可信资料传给模型，SYSTEM 只保留固定平台说明；管理员公共 Skill 保持原有受信上下文。现有工具权限、审批及输入数据处理规则继续生效。

## 7. API 与代码落点建议

端点命名为建议，不属于已确认的接口契约：

| 端点 | 职责 |
| --- | --- |
| `GET /api/v1/skills` | 公共 + 本人可用目录，保留聊天入口并增加来源 |
| `GET /api/v1/me/skills` | 本人未删除的管理列表，含停用项 |
| `POST /api/v1/me/skills/parse` | 单个 .md 校验与解析，仅返回编辑表单内容，不落库发布 |
| `POST /api/v1/me/skills` | 根据表单创建个人 Skill 并启用，支持幂等键 |
| `GET /api/v1/me/skills/{id}` | 本人详情及当前编辑内容 |
| `POST /api/v1/me/skills/{id}/versions` | 保存编辑，追加版本、切换当前版本并启用，校验 revision 和幂等键 |
| `PATCH /api/v1/me/skills/{id}` | 按 revision 启停，不开放公共管理配置或脚本审批字段 |
| `DELETE /api/v1/me/skills/{id}` | 按 revision 删除，保留版本 |

首期不必开放个人历史版本回滚页面；保留历史数据和 Run 回溯即可。写接口沿用现有 origin 校验、认证及错误投影，不仅依赖前端按钮隐藏。

实施涉及：

- 后端 `domain/skill/{model.py,ports.py}`：归属、删除、来源及身份相关端口。
- 后端 `app/skill/{service.py,package.py}`：个人文档校验、管理流程、目录；可拆小型个人文档解析模块，避免让管理员 ZIP 路径承担两种权限策略。
- 后端 `adapter/skill/{model/skill.py,repository.py,converter/skill.py}`：迁移映射、归属条件、唯一性和事务；接口实现继续显式声明端口。
- 后端 `api/skill.py`、`api/dto/skill.py`、`api/converter/skill.py`：个人路由、严格输入 DTO、目录来源。
- 后端 `adapter/run/repository/lifecycle.py` 及 Run DTO/converter：提交、重试快照身份参数和来源兼容。
- 前端 `features/skills/`：我的技能列表和编辑导入弹窗、API/hooks、目录来源展示；`app/AppRoutes.tsx`、`AppShell.tsx`：本人页面入口。

前后端明确分工。必要步骤写简体中文注释说明归属边界、版本发布事务、删除后的历史读取意图。

## 8. 迁移与兼容

1. 检查实施时实际迁移 head 后追加迁移，不修改已执行迁移。
2. 全部既有 Skill 回填 public、owner_id=null、deleted_at=null，保留启用状态、版本及脚本审批配置。
3. 调整 slug 唯一范围和包哈希索引，增加归属一致性约束；迁移前验证历史记录满足新约束。
4. 旧快照未携带来源时兼容为 public；不批量重建旧 Run 快照，不修改现有不可变版本内容。
5. 保持管理员 ZIP 功能和公共目录原有行为。回退到旧代码前必须处置新个人记录及索引差异，不能直接假定可逆降级。

无需新增外部基础设施，复用当前数据库、对象存储和 Run 机制。真实集成验证使用实施时当前 `.env` 配置的服务，不自行启动替代本地服务；临时测试数据隔离并清理，不打印凭据。

## 9. 验收条件

| 场景 | 可观察结果 |
| --- | --- |
| 在线创建 | 输入有效名称、描述和正文后保存，列表显示启用，新 Run 目录可见 |
| 文件选择 | 控件 accept 为 .md 且不可多选；手动选择或拖放其他类型给出错误 |
| 绕过前端 | API 直接上传 .py、ZIP、非法 UTF-8、超限文件或无效元数据均被拒绝，无版本发布 |
| 纯 Markdown | 无 frontmatter 可导入，补齐名称、描述后保存；任意 .md 文件名可用 |
| 执行声明 | 元数据 scripts/dependencies（包括空值）或请求额外执行字段明确报错 |
| 正文代码 | 含 Python/SQL 代码块可保存，但无脚本登记、依赖安装或 Runner 调用 |
| 双用户隔离 | A、B 可导入相同文档；B 的目录、管理、版本读取和伪造 Run 选择均不能访问 A 的个人 Skill |
| 公共和个人同名 | 同时显示且来源明确，加载始终按 ID 命中正确正文 |
| 自动与手动使用 | 个人项进入模型目录并可 skill_load；手动选择使用同一版本身份 |
| 权限不提升 | 个人指南不能绕过现有工具权限及审批；伪造个人脚本执行请求被拒绝 |
| 编辑发布 | 成功后新增版本并启用；旧 Run 加载旧正文，新 Run 加载新正文 |
| 停用与删除 | 新 Run 不再可用；正在执行、恢复执行及历史回溯仍读取原版本 |
| 重试 | 新 Run 重新校验本人可用范围；已失效的手动选择提示调整，不复活删除 Skill |
| 子 Run | 只继承父 Run 已授权目录，不读入其他用户或后来新增的私人 Skill |
| 冲突与失败 | 幂等重放不重复版本；旧 revision 保存失败保留输入；存储或数据库失败保留旧可用版本 |
| 删除竞争 | 保存与删除串行收敛，后到保存不能恢复已删除身份 |
| 兼容 | 既有公共 Skill 管理、脚本执行及旧 Run 快照读取回归通过 |

测试应覆盖服务/Repository 权限与事务、API 上传与越权、PostgreSQL 约束和对象存储、前端文件选择/错误保留/聊天来源展示，并以双用户浏览器流程验收。若执行真实模型验证，分别验证按需加载和手动选用；未运行时明确报告验证限制。

## 10. 实施顺序与准备程度

1. 后端 Implementer：迁移和模型、个人文档协议、归属 CRUD、目录和 Run 快照全链路，完成必要测试并给前端稳定契约。
2. 前端 frontend-implementer：我的技能页面、导入与编辑、启停删除、聊天目录来源，完成必要交互测试。
3. 独立 Reviewer 审查实际 Diff，重点核对用户隔离、无脚本路径、版本发布、删除历史兼容和迁移；发现有效问题交回对应 Implementer，修复后重新 Review，最多三轮。
4. Root 最终验收已确认规则、必要测试和阻断问题。

产品核心规则和整体实施已获用户确认，没有新增业务基础设施依赖。导入协议、迁移方案和 API 契约已作为前后端交接基线；如修改现有架构，按项目规则重新确认。真实迁移、对象存储、模型和双用户浏览器验收已在本地 Docker 测试环境补齐，验证边界见实施报告；目标环境仍待迁移和部署。
