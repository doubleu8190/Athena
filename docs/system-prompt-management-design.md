# 管理员系统提示词管理设计

日期：2026-11-11。状态：用户已确认整体方案并授权实施；前后端实现完成，terra-reviewer 独立复审均 PASS，Root 验收通过。后续真实端到端测试已应用开发库迁移，核心场景通过；未提交 Git。

## 1. 目标与已确认规则

管理员通过 Web 管理主对话和历史压缩两类系统提示词，每类各有一份全局当前配置。

- 仅管理员可查看管理页面、编辑、查看历史及恢复版本；普通用户使用系统配置，不提供配置入口。
- 完整正文可编辑，使用纯文本；首期没有变量、模板语法、草稿或单独发布流程。
- 点击“保存并生效”生成不可变历史版本，并切换当前版本。
- 两类提示词都在 Run 创建时固定；新配置只影响新 Run。同一 Run 的工具后续轮次、澄清恢复、审批恢复及压缩继续使用原版本。
- 历史记录包含正文、修改人和时间；恢复旧内容也生成新版本，不修改旧记录。
- 拒绝全空白内容；并发修改时阻止覆盖并保留输入；保存失败不改变当前生效配置。
- 提示词改变模型行为，不改变后端鉴权、工具审批和执行限制。

首期不包含按用户、项目、会话或模型定制提示词，亦不包含批量发布两类配置、版本删除、在线试运行或效果评测。

## 3. 页面与用户流程

以下为基于已确认规则的实施建议。

新增 `/admin/system-prompts`，在管理导航显示“系统提示词”。页面通过两个标签切换“主对话”和“历史压缩”。每类显示当前版本、修改人、修改时间、纯文本编辑框、“保存并生效”按钮和历史列表。

1. 加载当前正文及版本 ID，将版本 ID 作为本次编辑的基础版本。
2. 编辑后提交正文与基础版本 ID；保存过程中禁用重复点击。
3. 成功后展示新版本，更新当前内容、编辑基线和历史列表，并提示“已保存，新任务使用新版本”。
4. 历史列表分页加载；选择历史版本可只读查看完整正文，点击“恢复此版本”后生成新版本并切换当前配置。
5. 保存和恢复都检查基础版本；遇到冲突不自动重试、不自动合并，保留编辑文本并提示刷新。刷新前明确告知本地编辑将被替换，允许先复制内容。
6. 网络或服务错误保留编辑内容。若请求结果不确定，重新读取当前版本核实，不自动重复恢复操作。

切换类别或离开页面时，存在未保存修改则提示用户确认放弃。未修改内容时禁用保存；服务端对正文完全相同的提交返回当前版本，不制造重复历史，但仍先校验基础版本。

## 4. 数据与分层建议

不增加独立基础设施，使用现有 PostgreSQL、权限和前端请求体系。

### 4.1 持久化模型

建议使用两张表：

- `system_prompt_versions`：`id`、`kind`（`main` / `compression`）、`content`、`created_by`、`created_at`、可空的 `restored_from_version_id`。版本一旦生成不再修改或删除。初始版本允许系统来源；用户来源保留可追溯的操作者标识，不能因账号删除而级联删除配置。
- `system_prompt_settings`：`kind` 主键及 `current_version_id`。仅两行，分别维护两类当前版本。数据库约束或事务校验确保引用版本的类别匹配。

Run 增加 `main_prompt_version_id` 和 `compression_prompt_version_id`，都引用不可变版本。即使没有启用压缩策略，也绑定压缩提示词，保证 Run 创建时的配置语义完整。

保留 `prompt_template_version="run-v2"` 作为既有执行协议，不将提示词 ID 填入该字段。压缩策略既有 `prompt_template_version` 保留为模板协议元数据，不再作为可编辑正文的来源。摘要新增 `compression_prompt_version_id`，记录实际产生该摘要的正文版本；已有 `prompt_version` 保留协议含义，避免混用。

版本引用使用限制删除；不设计运行时静默降级到“最新版本”或代码常量。正文持久化仅一份，Run 引用版本即可，无需再存一份重复正文快照。

### 4.2 模块职责

- `domain/system_prompt`：类别、版本、输入、错误及显式仓储接口。
- `app/system_prompt`：管理员授权、查询、保存和恢复用例；不包含 ORM。
- `adapter/system_prompt/model`、`repository`、`converter`：数据库映射、事务和转换，明确实现领域接口。
- `api/system_prompt.py` 及对应 DTO/converter：管理员 HTTP 接口；沿用 `AdminAuth` 和写请求来源校验。
- Run adapter 在原有创建事务内读取当前版本，不调用另起事务的配置查询来固定版本。可通过共享 AsyncSession 的内部仓储方法复用读取逻辑。
- 执行准备阶段解析 Run 已绑定的不可变版本，将正文显式传入上下文构建和压缩调用；不在同步纯函数里访问数据库。恢复执行时仍按相同 ID 解析。
- `frontend/src/features/admin`：复用现有 API、hooks、query keys、错误展示和分页方式，新增管理页面。

## 5. 接口建议

所有接口位于管理员命名空间；普通用户直接访问也由后端拒绝。

| 方法与路径 | 行为 |
| --- | --- |
| `GET /api/v1/admin/system-prompts/{kind}` | 返回当前正文、版本 ID、修改人和时间。 |
| `GET /api/v1/admin/system-prompts/{kind}/versions` | 分页列出历史元数据，按时间及 ID 稳定倒序。 |
| `GET /api/v1/admin/system-prompts/{kind}/versions/{id}` | 返回同类别历史版本完整正文。 |
| `POST /api/v1/admin/system-prompts/{kind}/versions` | 提交 `content`、`expected_current_version_id`，原子创建并切换版本。 |
| `POST /api/v1/admin/system-prompts/{kind}/restore` | 提交 `source_version_id`、`expected_current_version_id`，从同类别历史内容生成新版本并切换。 |

建议空白或非法类别返回 422，版本不存在或类别不匹配返回 404，并发冲突返回 409 `system_prompt_version_conflict`；身份、权限和来源错误沿用项目现有约定。冲突响应可包含当前版本 ID，不返回无关配置。正文保留换行与原始排版，以去空白后的结果检查非空，不擅自 trim 后存储。

建议初期正文上限为 100,000 个字符，前后端一致校验；这是实施参数建议，并不代表正文一定能装入任意模型窗口。超出实际上下文窗口时沿用现有预算检查和失败语义，不截断系统提示词。

## 6. 事务、并发与运行语义

### 6.1 保存和恢复

同一数据库事务内锁定该类别 settings 行，比较 `expected_current_version_id`；不一致立即报冲突。校验通过后插入不可变版本并更新指针，一起提交或一起回滚。恢复额外校验源版本属于该类别。保存与恢复都以指针切换提交为生效点。

并发相同请求只有一次能成功切换；后续请求基线已过期则返回冲突。网络超时后不自动重新提交；客户端可读取当前内容核实。首期不新增独立保存请求幂等表。

### 6.2 Run 创建与重试

submit/retry 在现有事务内、幂等重放检查之后读取两类当前版本并写入 Run。使用单条读取语句获取两类指针，使它们对应同一数据库可见快照；每类独立发布，不保证两类配置构成某个共同发布批次。绑定选择的线性化点是该次数据库读取，和管理员保存并发时，Run 可绑定读取时可见的旧版或新版；保存成功后才发起创建的新 Run 必须读到新版。

保留 Session 锁、模型/策略锁顺序和既有幂等规则，不为提示词读取新增反向锁依赖。已绑定的历史版本不可变且不可删除，因此读取后即使当前指针更新也可安全使用。

- 新 submit：绑定当时当前版本。
- 用户重试失败任务：已有实现创建新 Run，因此绑定当时当前版本；原 Run 不变。
- 同一 request ID 的幂等重放：返回原 Run，不重新绑定版本。
- 澄清回答、工具审批恢复、Worker 再次领取原 Run：保留原引用。
- 历史版本缺失或类别损坏：按明确配置错误结束执行，不回退最新正文；记录安全错误码，不将完整提示词写入普通日志。

### 6.3 压缩和 Token 预算

`_render_compression_request`、批次切分、摘要再压缩及 `_summarize_batch` 都接收同一 Run 绑定的压缩正文，避免估算与实际发送不一致。主提示词同样必须在所有上下文和回退路径中计入 Token。

既有摘要是历史执行结果：修改压缩提示词不重写或自动删除已有摘要。新 Run 可继续复用符合现有 cutoff/覆盖规则的旧摘要；需要进一步压缩时使用新 Run 绑定的版本，并记录新摘要版本来源。若希望强制按新提示词重算全部历史，将属于额外功能，不包含在本期。

压缩失败是否回退完整上下文、失租后禁止发布摘要、模型禁用和调用预算限制均沿用现有机制。

## 7. 初始化与部署边界

新增数据库结构并写入两类初始版本，正文取当前代码常量原文；创建两行当前指针。初始化必须可验证且不得在每次服务启动时覆盖管理员已保存内容。

本项目处于开发阶段，不增加旧执行协议兼容框架或历史数据迁移产品功能。实施时应明确选择开发数据库重建，或必要的加字段及初始值填充方案；不得擅自清库。若保留既有 Run/摘要，可将其固定引用填为本次初始化的原始正文版本，使原有语义保持可解释。结构变更前应停止创建/执行任务，完成初始化与引用完整性检查后统一启动，避免新旧进程并行造成无版本引用的数据。

## 9. 可观察的验收条件

- 管理员可读取和完整编辑两类提示词；普通用户无法访问页面或直接调用管理接口。
- 保存 A 为 B 后，新 Run 的主请求及压缩请求使用 B；已排队、执行中、等待澄清或审批的旧 Run 继续使用 A，包括跨 Worker 恢复。
- 重试产生新 Run 使用 B；幂等重放原提交/重试请求返回相同 Run 和原引用，不生成新任务。
- 两位管理员基于同一版本保存时只有一位成功；另一位收到 409，输入仍在，历史无失败操作产生的孤立版本。
- 空白和超限输入被拒绝；事务写入失败时当前指针和历史一起回滚；正常正文换行保持原样。
- 恢复旧内容生成新 ID，记录恢复来源和操作者；原版本保持不变；跨类别恢复被拒绝。
- 压缩 Token 估算和实际请求使用相同正文；长提示词纳入预算，无法容纳时按现有边界失败且不截断。
- 压缩修改后旧摘要仍可使用；新生成摘要记录实际压缩提示词版本；失租、校验失败时不发布摘要。
- 模型调用失败、完整上下文回退、final-only、工具后续轮次均保持主提示词版本一致；修改正文不绕过工具权限及审批。
- PostgreSQL 集成测试覆盖保存竞争、事务回滚和 Run 绑定；必要单元测试覆盖正文传递与预算路径；前端覆盖编辑、冲突保留、历史恢复和权限。运行相关既有测试、前端类型检查及构建。
