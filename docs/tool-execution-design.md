状态：产品闭环和首期实施范围已确认，并已授权按精简方案实施；待独立 Review 与最终验收。
核对日期：2026-11-09。本文不表示 Review PASS，实际验证结果以交付报告为准。

首期精简范围：原 Worker 失租恢复、deadline 或取消后的迟到结果结算、同一 Run 内 MCP 会话复用、跨 Run 自动结果复用，以及细粒度 unknown/retry 链暂不进入首期实现。本文只描述首期规则，后续能力仅保留末尾清单；具体实施以 docs/tool-execution-implementation-plan.md 为准。

## 1. 目标与已确认范围

在已有 Run 内实现完整闭环：模型选择工具 → 服务端执行 → 保存 Execution 调用与结果 → 交回模型 → 继续调用或生成最终回答。

首期同时支持管理员注册的 MCP 工具与平台内置工具。内置工具直接调用应用服务，不伪造 MCP Server 或 MCP 工具记录。保留现有 request_user_input 澄清流程。

已确认的内置工具为 memory_search、knowledge_search；不包含记忆写入、文件修改或命令执行内置工具。MCP 可以执行管理员配置的读写能力。管理员配置可信能力，普通用户使用，无需逐次审批。

以下产品规则已经确认；后文具体表、端点、状态名和模块拆分是待整体确认的实施建议。

### 1.1 可用范围

- Run 可使用管理员已注册目录中的全部 MCP 工具；普通用户不手工选择工具。
- 内置工具由平台明确注册；依赖功能未启用时不提供给模型。
- 所有执行都校验当前用户与聊天上下文，管理员身份不扩大个人数据查询范围。
- memory_search 查询当前用户个人记忆和当前项目记忆。
- knowledge_search 只查询当前项目关联且当前用户仍有权访问的知识库。没有项目或没有可用知识库时不提供该工具，不自动搜索用户全部知识库。
- 已确认：每项目最多绑定 20 个知识库，第 21 个绑定返回明确错误；重复绑定保持幂等，不额外占名额。并发绑定在项目行锁下检查并提交，保证不突破上限。knowledge_search 搜索全部有效关联库，保留现有单次最多 20 库的检索限制，不新增分批检索合并。
- 模型不能指定 owner、聊天 ID 或知识库范围来扩大访问；这些信息由服务端注入。

### 1.2 执行与限制

- 模型每轮最多调用一个工具，同一 Run 可连续调用多个工具。
- 参数错误和明确失败返回工具结果，由模型决定修正、换工具或向用户说明。
- 执行层不自动重试，包括只读内置工具。
- 业务工具产生 unknown 时，保存安全结果并直接失败 Run，不再请求模型或工具；用户通过查询查看情况，再决定是否主动 retry。
- 每 Run 默认最多 40 次实际 LLM 请求，包含正常生成、压缩和模型请求重试，跨澄清累计。工具执行本身不计次数，不另设工具调用次数上限。
- 单次工具默认 30 秒，且不超过 Run 剩余执行时间。
- 单次保存、展示并交给模型的工具结果默认最多 64 KiB，另受模型上下文预算约束。超长结果明确标记截断。
- 上限为部署配置，普通用户与模型不能提升。
- 已确认时间预算按执行段计算：每次从 queued 领取进入 running，最多执行 300 秒，模型配置可收紧。进入 waiting 后不计等待时间，用户回答后重新领取获得新执行预算；同段内工具调用不重置截止时间。单工具 30 秒包含在当前执行段预算内。LLM 请求次数跨澄清累计，不随新执行段重置。
- 资源清理可在业务执行预算外额外使用最多 10 秒，仅用于取消请求、关闭连接及回收进程，不再执行业务；不能按 Server 数量重复获得清理预算。
- 剩最后一次 LLM 额度时仅允许最终回答，禁用工具（含澄清）及压缩；无法容纳上下文则明确失败。额度耗尽不追加请求，仍遵守时间限制。

### 1.3 停止、崩溃与目录变更

- 停止后不发起新调用，尝试取消当前调用；有界清理后收敛为已取消。
- 取消不撤销外部效果。不能确认外部执行结果时保留结果未知记录。
- 心跳失败或失租后停止本地执行，不尝试恢复租约；其他 Worker 只回收并终结 Run。
- 先持久化调用记录，再执行。同一 Run 的已保存结果不重做；已进入执行阶段但没有结果的调用不重放，收敛为结果未知，包括记录后、发出请求前的崩溃窗口。
- 原 Worker 崩溃后，另一 Worker 只负责回收并终结失租 Run，不自动恢复同一 Run 的模型循环。有 unknown 调用时，向用户说明结果未知及重复执行的可能影响，由用户决定是否重新执行；未经用户决定不自动重试。
- Run 开始时固定工具名称、描述、参数定义。调用前复核 MCP 来源配置版本；服务删除、配置更新或工具移除时不发出旧调用，返回工具变更或不可用。
- 配置变更不撤销已准入调用；结果仅在 running、有效租约和 deadline 内保存。新增工具和新配置从下一 Run 生效，澄清恢复沿用原工具定义。
- 每次工具调用独立建立并关闭 MCP 连接，不持有跨调用会话。

### 1.4 可见记录

每次调用展示名称、状态、开始时间、耗时、可展开参数与结果；检索结果带片段及来源标识。明确区分失败、取消、结果未知。调用与结果保存在 Execution 消息，聊天正文保留助手说明与最终回答。不输出 MCP 地址、凭据、进程原始 stdout/stderr 或内部异常。

在 running、有效租约和 deadline 内，MCP 已返回明确成功但交付前认证失效时，调用仍保存为 completed 并保留结果，不改为 unknown；停止后续模型和工具调用，Run 以认证失效原因失败。认证失效期间不向模型或客户端交付结果；用户重新登录且仍有该聊天访问权限时可查询。内置检索未通过交付前权限复核时丢弃内容，只保留安全状态记录。保存已知外部执行事实与交付数据的权限校验分别处理。

## 3. 架构与职责（实施建议）

沿用 api → app → domain 及 adapter 实现边界，不建立独立工具服务或新任务队列。

- domain/tool：增加通用运行工具定义、可信上下文、执行结果和执行端口；保留现有 MCP 目录类型兼容性。运行定义区分 builtin/mcp 来源，不要求内置工具拥有 server_id。
- app/tool：组装安全运行目录、按固定定义验证参数、分派内置/MCP、规范化结果。模型名称只用于查服务端映射，不通过拆解名称推测路由。
- app/tool 内置处理器：调用 MemoryService、ProjectKnowledgeService、KnowledgeService 和 Session 公共接口。认证 session 与聊天 Session ID 明确区分。
- domain/mcp + infrastructure/mcp：新增窄调用端口和受控 SDK 实现；连接凭据只在此边界使用。
- app/run：负责模型循环、调用预算、租约与持久化边界，不把 MCP 协议细节塞入执行器。
- adapter/run：实现快照和调用状态的原子提交；api 仅提供用户可见投影与事件，不提供普通用户任意 tools/call HTTP 入口。
- main.py、run_worker.py：HTTP 与 Worker 装配同一配置、注册表及依赖。

不新增通用插件框架、工具编排 DSL、Redis 工具缓存、连接池或自动工具选择检索。目录过大时按模型工具数量/上下文限制明确失败，不静默挑选部分工具。

## 4. Run 工具快照与调用前校验（实施建议）

建议在 Run 首次领取且首次模型请求前，以有效执行租约原子固定快照；后续领取或澄清恢复不得替换。排队期间尚未使用工具，取首次启动时的最新目录。是否改为提交 Run 时固定，属于可调整的实施时点。

快照包含公开名称、描述、Schema、工具稳定 ID、类型、内置版本或 MCP server_id、remote_name、config_version。内部映射不可进入公开 DTO。快照不保存凭据、URL、command 或 env；不会因 MCP 被物理删除而丢失历史记录。

已确认容量限制：完整目录最多 200 个工具（含 MCP、内置和澄清工具），完整快照序列化 UTF-8 JSON 最多 2 MiB（含 Schema 和内部路由映射）。分页读取时累计检查，超限在持久化前以安全错误结束 Run，不保存半份快照或静默裁剪；模型上下文预算另行独立检查。

每次调用先校验当前账号、聊天和 Run 执行权，再按快照解析工具。MCP 读取当前配置和版本；只允许与快照版本一致的配置。该读取定义调用准入时点；准入后管理员修改不撤回已准入调用，避免持有数据库锁跨越网络调用。

内置工具执行时重新解析当前项目和访问范围。建议对知识库使用“快照范围与当前有效关联的交集”，解除关联立即停止使用，新增关联从下一 Run 生效；这一范围收缩细节待整体确认。内置检索返回结果前复核权限，权限失效丢弃内容；MCP 明确成功后的认证失效遵循 1.4 的执行事实保留规则。

平台工具定义版本在存续 Run 期间须可解析；版本不支持时返回不可用，不能把旧名称默默绑定到新语义。

## 5. 执行流程与消息

1. 读取固定 Run 上下文、工具快照和累计 LLM 请求数，计算包含工具 Schema 的输入预算。
2. 模型请求沿用原生 function calling，关闭并行调用。多调用响应作为协议异常处理，不执行其中任何一个。
3. 对单调用验证名称、参数对象、Schema、执行上下文与剩余预算。使用本地 Schema 校验，禁止远程 $ref 网络解析；供应商格式转换不改变业务校验语义。
4. 通过原子 begin 命令保存 assistant ToolCallPart、调用状态与开始事件；在仍为 running 且租约有效时取得唯一执行准入。提交失败或提交结果不明确时不发外部请求。
5. 执行一次处理器，遵守工具 deadline；清理另有部署有界预算，用户取消向下传播。
6. 规范化结果，经权限复核和大小限制后，原子保存 ToolResultPart、调用终态及事件。
7. 工具结果为 unknown 时，保存调用结果并失败 Run，不继续循环；其他结果使用相同 tool_call_id 构造协议，重新计算预算后继续请求模型。正常最终回答沿用原 finish 命令。
8. request_user_input 沿用 waiting/answer 流程；业务结果不当成新用户消息，也不复制成聊天最终回答。

参数无效和不可用也保存调用/结果对，不计工具额度；后续实际 LLM 请求消耗统一额度。最后一次请求禁用全部工具（含澄清）和压缩，若仍返回调用则明确失败。

已确认校验边界：LLM 适配器负责协议结构、调用 ID、参数可解析为 JSON 对象及大小限制；工具名称是否存在、是否可用及参数是否符合工具 Schema，由工具执行层校验。未知工具或 Schema 不匹配保存调用与错误结果并交回模型修正，不发出工具请求。无法解析的 JSON、缺失调用 ID 等仍属于协议失败，结束本次执行，不构造合法业务调用记录。当前 Chat Completions Adapter 遵循该边界。

模型在工具调用同一响应中带出的文字建议作为 Execution 中的说明保存，避免被当成最终答案；流式临时文字与最终正式消息替换关系沿用现有机制，并增加轮次标识以免后轮覆盖前轮。

## 6. 持久化、并发和状态（实施建议）

建议增加一张 run_tool_calls 表，作为执行准入和调用状态依据；协议内容仍只存 Execution 消息，通过消息 ID 引用，避免重复保存完整参数/结果。

最小字段：id、run_id、session_id、tool_call_id、ordinal、tool_id、tool_kind、execution_epoch、status、call_message_id、result_message_id、started_at、finished_at、safe_error_code、outcome。唯一约束为 (run_id, tool_call_id)、(run_id, ordinal)。字段长度和调用 ID 校验在实施时明确。

建议状态：executing、completed、failed、cancelled、unknown。结果另有稳定安全 code、message、data、truncated；明确业务失败与远端效果未知不可混淆。开始时间为进入执行阶段时间，不声称等于远端执行时间。

Run 工具快照建议作为 Run 上类型化 JSON 字段保存；所有数据库 JSON 使用显式 Pydantic 模型及统一 JSON 工具。只限制实际 LLM 请求次数，删除工具计次标记；ordinal 仅表示工具记录顺序。首期使用 Run 的原子 llm_request_count 计数，不建立逐请求准入记录，也不从工具记录或 usage 推导。

原子边界：

- begin：锁 Session → Run → 调用记录，校验 running、worker/epoch、有效租约及 deadline；原子保存调用与开始事件，只有首次成功准入可执行。
- complete：仅在 running、有效租约及 deadline 内幂等保存结果；unknown 同事务失败 Run，不再进入模型循环。
- 所有 Run 终态事务统一收敛未完成工具调用：复用一个事务内辅助函数，为 executing 调用补齐 unknown、安全 ToolResultPart 和结束事件；保留已有确定结果。不允许终态 Run 遗留 executing 或缺少结果的协议调用。
- 现有 fail（包括执行超时及普通异常）、取消结算和失租回收都调用该辅助函数；正常 finish 也保证没有未结算调用。先补齐结果再清除租约、提交终态，不能依赖之后的回收器修复已终结 Run。
- 取消、超时和失租后不接收迟到结果，资源仅做有界关闭；旧 Worker 不能覆盖 unknown 或终态。

数据库事务不跨越工具网络或进程等待，不保证远端操作与本地提交恰好一次。

### 6.1 用户主动 retry

用户 retry 创建新 Run，从头执行，不自动恢复、复制或复用原 Run 的工具结果。来源 Run 有 unknown 时，必须通过 confirm_unknown 整体确认后创建新尝试；旧 unknown 保持不变。不遍历 retry 链，不支持逐调用确认。

所有 retry 均须在后端查询/接口说明中明确告知：“整个任务将从头执行，可能重复此前已成功的操作；原操作结果未知时也可能已生效。”该说明不局限于 unknown，且不增加正常工具执行的逐次审批或自动结果复用机制。

## 7. 内置工具（实施建议）

两者均为只读，不改变查询核心服务权限模型。模型参数只接收 query、limit；拒绝额外字段、空查询、布尔 limit 及越界数量。

### memory_search

复用 docs/memory-query-tool-design.md 的 query 最大 2000 字符、limit 默认 5/最大 8、召回预算 1200 tokens 建议。服务端由当前用户与聊天项目构造 personal/project scope；集中复用映射，不让模型提交 scope_key。返回 memory_id、version、content、personal/project 范围；首期不输出未经权限接入的原始记忆来源。

区分正常空结果、降级、读取关闭、服务不可用、参数无效和权限拒绝；不可把禁用或检索失败说成没有历史记忆。

### knowledge_search

经 Session 公共接口获取项目，再经 ProjectKnowledgeService.list 获取当前关联与可见知识库，调用 KnowledgeService.search。建议 query 最大 4000 字符、limit 默认 5/最大 8，模型不能指定 base_ids 或提高 context_budget。

结果包含文档名称、命中片段与可授权解析的 base/document/version/chunk 来源标识；来源读取必须沿用现有权限接口，不暴露存储键或本地路径。返回降级通道说明和截断信息；零命中与检索不可用区分。

## 8. MCP 调用与结果边界（实施建议）

新增调用适配器复用受控 HTTP/stdio 传输实现，每次工具调用独立建立、协商并关闭连接；不复用 MCP 会话或 stdio 进程。每次调用前复核当前配置版本，连接建立及协商计入单工具 30 秒预算。异常、取消或超时后有界清理，不自动重发调用，不重新发现并替换固定目录。

SDK mcp==2.3.0 已在仓库锁定，但本次没有验证真实调用 API、自动重发、取消通知、现代/legacy 调用兼容和结果内容行为。实施阶段先对锁定 release 的源码与官方资料做能力核验和可执行验证，不照搬主分支接口。

必须验证：一次业务请求最多发出一次；协商、重连或协议回退不能重复业务调用；HTTP 凭据不串用；DNS/IP/TLS/重定向策略仍生效；stdio 正常退出及 TERM/KILL 清理有界。无法满足时为依赖阻断。

MCP 原生明确错误结果转为失败；请求可能已发出后的协议错误、超时、响应读取中断或无法解析结果保守记 unknown。已收到可信业务成功但清理失败，保留已知业务结果并另记清理错误，不误导为业务失败或诱导重试。

已确认：MCP 首期只支持文本及有界结构化 JSON 结果，不自动下载图片、音频、资源链接或读取远端 URI。其他内容类型以受限的不支持说明表示，不宣称完整多模态 MCP 支持。

传输读取上限与 64 KiB 展示上限分开：前者在 SDK 解析前控制内存，后者限制规范化结果。结构化内容按条目裁剪或转成有效 JSON 包装，不能截断 JSON 字节形成非法协议。仅保存截断投影，不建立未设限的原始结果仓库。

远端文本视为工具数据，不当成系统指令。应用不拼接秘密、原始异常或 stderr；无法保证远端业务文本语义上不包含敏感内容，应由管理员选择可信 Server，不能承诺通用语义脱敏。

## 9. 上下文、事件和 API（实施建议）

每轮重建包含本 Run 已提交调用/结果的合法协议；压缩不得拆散一组调用/结果，未结算调用不能进入下一模型请求。预算计入快照 Schema、协议、结果和最终输出预留。最后一次 LLM 请求仍检查上下文且禁用压缩，不能容纳则明确失败。

增加工具开始与结束的持久 RunEvent，复用当前 SSE 和数据库对账；事件仅带调用 ID 与安全状态，详情走现有授权读取或新增窄查询。若现有 Execution API 无法提供起止时间及耗时，可增加 GET /api/v1/sessions/{session_id}/runs/{run_id}/tool-calls；具体端点待整体确认。

已确认：前端页面不属于首期交付，仅交付后端持久记录、授权查询和事件契约。本文用户可见字段描述后端应提供的数据，不表示本次实现页面。后续前端使用安全投影，并通过持久记录对账，不依赖 Pub/Sub 成功来认定调用已完成。

## 11. 可观察验收条件

首期验收以 docs/tool-execution-implementation-plan.md 的第 9 节为准。

- 模型同一 Run 连续调用 MCP、memory_search、knowledge_search 后正常回答；真实 HTTP 和 stdio 调用均各只发出一次。
- 禁用依赖、无项目、无关联知识库时相应内置工具不进入模型目录；模型猜测工具名也不能绕过快照。
- 项目第 21 个知识库绑定被拒绝；满额时重复绑定已有库仍幂等成功。并发争抢最后名额只能新增一个关联，检索覆盖全部有效关联库而非静默取子集。
- 普通用户无法指定他人数据范围，权限撤销或关联移除后不返回原数据；管理员不越权。
- 参数失败保存合法调用/结果对且不发出请求；多调用响应不执行任何业务工具。
- 最多 40 次实际 LLM 请求（含压缩及模型重试），最后一次仅回答；澄清恢复不重置次数或工具快照，工具执行本身不计次数。
- 澄清等待不消耗执行预算，回答后重新领取获得最多 300 秒；同执行段内工具和续租不延长截止时间。单工具最多 30 秒且受剩余时间限制，执行到期后仅允许额外最多 10 秒资源清理。
- 工具超时不自动重试，外部可能已生效时标记 unknown；已知成功不被清理错误覆盖。
- 调用前取消不发出请求；调用中取消完成有界清理，不再调用模型/新工具，远端效果不被声称已撤销。
- 在开始记录提交前、提交后发出前、请求发出后、结果保存前后分别注入崩溃；不重放，未完成记录收敛 unknown。
- 旧代 Worker 完成与回收/取消竞争时只有有效写入生效，迟到结果不覆盖 unknown 或终态。
- unknown 结果保存后 Run 直接失败，模型和工具请求次数不再增长；fail、取消和回收等终态事务均无遗留 executing 调用，已有确定结果不变。
- 数据库 begin 提交结果不明确时不发工具请求；complete 重复提交不产生两条结果。
- 修改/删除 MCP 后拒绝旧快照的新调用；已准入调用使用原配置，凭据不进入快照、错误和公开事件。
- 同一工具每次独立建立并关闭连接，不自动重发。
- 大结果在传输与规范化阶段均受限；UTF-8 与 JSON 保持有效，展示标明截断，上下文与压缩保留合法协议。
- SSE 断线重连可从持久记录重建调用状态；所有调用查询都验证 owner 和 Session 可见性。
- 原 Worker 崩溃后，回收方补齐 unknown 并终结 Run，不自动重新排队或继续模型循环。
- 所有 retry 均明确提示从头执行可能重复已成功操作；有 unknown 时另外要求整体确认。新尝试不复用旧结果，旧 unknown 不改写。

验证应包含服务层测试、真实 PostgreSQL 原子性/竞争测试、受控 HTTP/stdio MCP 服务及模型多轮集成测试；不以 Mock 单测替代真实外部调用和并发证据。
